### The one finding that changes a fix's shape

**B10 has no serialization at all, and the code already locks the wrong row.** `recordDepositMovementTx` reads the parent with `findDepositForBusiness(tx, …)` — no lock — then sums movements, then checks `amountMinor > held`, then inserts. Two concurrent draws both read the same `held` and both pass.

The instinct is to lock `deposit_movement`. **That cannot work:** under `READ COMMITTED` a row lock on existing movements does not block a concurrent `INSERT` of a new one, because PostgreSQL has no predicate locking at this isolation level. The lock has to be on the parent `deposit` row.

And note what the code *does* already lock: `findObligationForDepositApply(tx, …, true)` takes `FOR UPDATE` on the **obligation**, and `deposit.ts:279` even reasons about "the same lock order `recordDepositMovementTx` takes". So lock discipline exists here — it is just pointed at the obligation and never at the deposit.

**Every writer must take the parent lock, or the serialization has a hole.** Enumerated:

| # | Writer | Route |
|---|---|---|
| 1 | `deposit.ts:58` `takeDriverDeposit` | direct insert |
| 2 | `deposit.ts:197` `recordDepositMovementTx` | direct insert — **the draw path, B10's own** |
| 3 | `deposit.ts:374` `takeCustomerDepositTx` | direct insert |
| 4 | `opening-balance.ts:247` | bulk `insertDepositMovements` |
| 5 | `opening-balance.ts:299` | the reversal path |
| 6 | `lease-closure.ts:381` | loops through #2, so covered by it |

Sites 1 and 3 create the deposit in the same transaction, so there is nothing yet to contend with — but they should still take the lock rather than rely on that staying true.

## Part 2 — The work, internally sequenced

**The sequence is not cosmetic.** Shipping the row-count assert before the locks turns a legitimate concurrent void into an unwarranted `500`. Locks first, then scoping, then the assert.

### Stage 1 · Migration `0031`

Three unrelated constraint changes plus B13's trigger, in one migration because NQ-1 put the trigger here.

**B20 — `CHECK >= 0` on the six columns that lack one.** Not `> 0`: `insurance_claim.received_amount_minor` and `incident_recovery.received_amount_minor` legitimately start at zero. Re-run the QA pre-flight first; it was clean on 23 Aug but that is a snapshot.

**B19 — the missing unique index.** The report's mechanism was wrong: concurrent submits do not `500`, they silently insert a duplicate claim.
```sql
CREATE UNIQUE INDEX incident_recovery_one_per_source
  ON incident_recovery (incident_id, source)
  WHERE voided_at IS NULL;
```
`WHERE voided_at IS NULL` is **not optional** — money is append-only and corrections void-and-replace (W-50), so an unconstrained `UNIQUE` would make a wrong claim permanently uncorrectable. Safe because `settleInsuranceClaim` overwrites `received_amount_minor` rather than inserting a second row.

**B13 — the archived-party guard trigger.** A `BEFORE INSERT` on each money table referencing a driver or customer, refusing a write against an archived party. Chosen over `FOR SHARE` on the money paths because it is CI-verifiable: *"did every write path take `FOR SHARE`?"* is answerable only by review, and a money path added next year would silently reopen the race.

### Stage 2 · Locks

**New capability, not a new argument** (B10): `findDepositForBusiness` gains `forUpdate`, following the shape already used 4× — a `forUpdate = false` default plus `const rows = await (forUpdate ? query.for("update") : query);`. Then all five real writers take it.

**`findObligationForBusiness` gains `forUpdate`** (B14b, B17). Same shape. The two handler read sites keep the default; the six domain sites opt in.

**Move the pre-checks inside their transactions** (B12, and `voidAdvance` with it). Both currently read with `writer` before opening a transaction.

**Move `assertArchivable` inside** (B13). The archive-vs-archive half already works via `archiveDriverRow`'s `WHERE` guard — leave that alone and do not re-derive it.

### Stage 3 · Correctness

**B5 — pass `tx`, six sites.** An argument swap, not a signature change: `resolvePeriodLinkage(db: ReadDb, …)` already accepts a transaction handle, which is why `deposit.ts:46` and `payment.ts:61` already call it correctly.

**B15 — move the linkage above the writes, three sites** (`payment-correction.ts:104`, `write-off.ts:77`, `:165`). Canonical order is linkage first, as `deposit.ts:46` does. Fails fast instead of rolling back work.

**B11 — `allocateAgainstOldest` returns the unallocated remainder**, both copies, and each caller asserts it is `0n`. A signature change, not a call-site tweak.

**B18 — pin the four trigger messages in a regression test.** Not a code fix: the matchers stay as they are, and the test fails loudly if a migration ever reworks the message text they depend on.

### Stage 4 · Scoping and the assert — last

**B14a — `AND business_id = ?` on all three `UPDATE`s**, plus a row-count assert.

Making the new `businessId` parameter **required** lets the compiler enumerate every call site; there is no way to silently miss one, which is the actual risk a staged rollout exists to avoid. Drizzle's portable row-count idiom across both drivers is `.returning({ id: obligation.id })` and checking `result.length === 1`, not a driver-specific `rowCount`.

**Per Q-1: a 0-row result throws `500 INTERNAL_ERROR`, logged with a stack trace. Never a 4xx.** Post-lock and post-scoping, zero rows cannot be legitimate user error — it means a tenancy bug slipped every earlier guard, or an impossible concurrent-delete race. The transaction rolls back, so nothing is half-written.

## Part 4 — The three open items, resolved

### 1 · CI verifies the trigger the same way it already verifies the other two — **catalogue-driven, not a list**

The existing `assert-no-trigger-drift.sql` checks `_period_open` and `_audit` on every table carrying `posted_period_id`. The archive guard belongs on a **different set**, so it needs its own assertion — but the same shape, and it rides the existing `check:drift` wiring into `integration.yml`, `deploy-qa.yml` and `migrate-production.yml` with no new plumbing.

**The set, discovered against the live QA schema rather than assumed — 8 tables, 11 party columns:**

| Table | Party columns |
|---|---|
| `advance` | `driver_id` |
| `day_record` | `driver_id` |
| `obligation` | `party_customer_id`, `party_driver_id` |
| `offset_record` | `driver_id` |
| `payment` | `party_customer_id`, `party_driver_id` |
| `trip` | `customer_id`, `driver_id` |
| `write_off` | `party_customer_id`, `party_driver_id` |

The membership test is *"carries `posted_period_id` **and** a party column"*, so the assertion derives its own list from `pg_attribute` and cannot drift the way a hand-maintained array does. **This is the whole reason the trigger beat `FOR SHARE`**, and it is now cashed rather than assumed.

**The migration attaches by the same catalogue query it asserts on**, so attach and check share one definition of the set. Note the known limit this inherits: like `0002`'s block, it **runs once** — a party-referencing money table created later gets no trigger from it. That is precisely what the assertion is for, and it fails CI rather than going quiet. (Checked against the next table due: GAP-185's `loan_payment` references `loan_id`, and `vehicle_loan.liability_owner` is an `app_user`, not a driver or customer — so it is outside this set and needs nothing.)

### 2 · **`INSERT` only.** An `UPDATE` trigger would break a documented guarantee

**The data could not answer this and it is worth saying so plainly:** QA holds **zero archived drivers and zero archived customers**, so there is no evidence to read. Queried, found empty, reasoned from the specification instead — the empirical route was a dead end, not a confirmation.

The specification settles it:

- **W-60** refuses archiving *"while any money tied to him is still **open**"*. So archival happens only once nothing is open. What remains is **settled history**.
- **U-5** promises *"every figure can be corrected later, with the change recorded"*, and **W-50** makes that correction a void-and-replace — which sets `voided_at` **by `UPDATE`**.

So voiding an archived driver's historical obligation is a legitimate, documented correction performed as an `UPDATE`. **A trigger firing on `UPDATE` would refuse it**, breaking U-5 to enforce W-60 — and W-60 never asked for that. There are **22 `UPDATE` call sites** across those eight tables; an `UPDATE` trigger puts every one of them in scope for a rule none of them is the target of.

`INSERT`-only also states the rule correctly: archiving means **no new money against this party**, not *this party's past is frozen*.

**The edge, and it resolves cleanly.** A late fact arriving for an archived party (§6.14/W-35 — a fine after the deposit went back) is an `INSERT` and *will* be refused. The path is to unarchive, record it, re-archive — `unarchiveDriver` and `unarchiveCustomer` both already exist (`party-archive.ts:167`). That is the honest answer rather than a hole: a party still receiving charges is not gone, and being made to say so is the point.
