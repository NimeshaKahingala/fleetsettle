## 1. The one finding that reorders the plan

**Track B cannot create a second business until Track C's schema has landed — not "should ship after," *cannot function at all*.** This is not in the design doc's dependency table (§1, "B depends on A; C depends on A"), and it is the single most important correction this pass makes.

`createBusiness` (`api/src/domain/setup.ts:46-101`) and `redeemInvite` (`api/src/domain/membership.ts:189-259`) are the **only two places business membership is ever created**, and both use the exact pattern CLAUDE.md prescribes everywhere else in this codebase ("the period-open trigger is the truth; do not pre-check in application code" — the same argument is written out in full at the top of `api/src/db/pg-error.ts:1-8`): no application-level check for "does this identity already have a business," just a `try`/`catch` on the DB's own unique violation.

```ts
// setup.ts:96-98, and membership.ts:255-257, identically
if (isUniqueViolation(err, "one_active_business_per_user")) {
  throw new BusinessAlreadyExistsError();
}
```

`one_active_business_per_user` (migration `0003`) is a **global** partial unique index — at most one active `business_member` row per user, full stop, no threshold, no counting. As long as it exists, the second `POST /api/business` from any user 409s **before** Track B's new threshold-counting logic (§7.4 of the design) is ever reached. Businesses 2 through 5 — the entire "auto-approve under the threshold" behaviour decision 4 describes — are unreachable until this index is gone. Track B's own test list (design §10: "Request 6 queues; approval runs `createBusiness` and produces a working business") **cannot be written**, because there is no way to get a test identity to business #2 in the first place while this index stands.

The design's §7.4 says the under-threshold path "runs the existing `createBusiness` transaction *unchanged*." It cannot be unchanged: the catch clause above references a constraint that Track C's own migration (§6.2, `DROP INDEX one_active_business_per_user;`) deletes. Post-migration this is dead code matching nothing — silently, not a compile error, not a test failure until someone specifically tries a double-submit race and gets an uncaught 500 instead of the intended 409. Both catch sites need this branch replaced, not left standing.

**The corollary that matters more than the numbering:** simply dropping the index without also shipping the `resolveMembership` rewrite (design §7.3) in the same unit of work is actively dangerous, not merely incomplete. Today the index is *why* `queries/identity.ts`'s `or()`-join cross-product (§7.3's own finding, confirmed independently at `identity.ts:56-64`) is latent — `.limit(1)` masks it, and the row count the join can actually produce is capped at one by the index it's paired with. Remove the index alone and a user who reaches two active memberships (which the drop makes possible) starts feeding an **ambiguous, cross-joined row** into `authMiddleware` on every request — the exact "confident, plausible, wrong number" class this document warns about elsewhere (§8.1), except upstream of the query that decides which business is even in scope.

**Resequence around this.** The real unit of work is not "Track B" vs. "Track C" — it is:

| Unit | Contents | Must land as one transaction/PR, atomically |
|---|---|---|
| **Phase 1 — multi-membership plumbing** | `DROP INDEX one_active_business_per_user`; the driver-linkage constraint rename (design §6.2's second half); `resolveMemberships` rewritten to `UNION ALL` (§7.3); `authMiddleware`'s five-step header rule (§7.2); `BUSINESS_NOT_SELECTED` added to `packages/shared/src/errors.ts`'s `ERROR_CODES`; the two now-dead `isUniqueViolation(err, "one_active_business_per_user")` catch clauses in `setup.ts` and `membership.ts` removed or replaced | **Yes — the index drop and the join rewrite are one deploy, never two** |
| **Phase 2 — platform tier** | `platform_admin`, `business_creation_request`, `platform_audit_log`; the threshold-counting `POST /api/business`; `/api/admin/*`; the admin panel | Depends on Phase 1 having shipped |
| **Phase 3 — business switcher** | Client-side selection, persistence, `X-Business-Id` injection, the switcher `Sheet`, `FirstRunGate` rebuild on `/api/session` | Depends on Phase 1's header contract; independent of Phase 2 otherwise |

This makes the design doc's original B/C split still correct at the *feature* level (the admin panel and the switcher genuinely don't need each other) — it was only ever wrong about where the schema boundary sits. Phase 1 is what the design called "half of Track C" and treated as shippable alongside or after Track B; it is neither — it is a prerequisite to both.

**Migration numbering, corrected:**

- `0029_multi_business_membership.sql` — Phase 1's schema half: the index drop and the driver constraint rename. (Design's §6.2, unchanged in content, moved earlier.)
- `0030_platform_tier.sql` — Phase 2's three new tables. (Design's §6.1, unchanged in content, moved later.)

Confirmed against every remote branch as of this writing (`git ls-tree` across all of `origin/*`): no branch currently holds a `0029` or `0030` file, so this ordering is free to take. Design's open question 2 ("decide before either starts") is answered by this renumbering, not left open.

- `api/src/domain/setup.ts` — `createBusiness`'s caller (the `POST /api/business` handler) gains the threshold check. **Concrete race condition, not in the design doc:** decision 4's threshold is "a fixed constant counting active owner memberships" (§7.4), checked by reading a count and branching — this is a classic check-then-act race. Two concurrent `POST /api/business` requests from a user sitting at 4 active ownerships can both read `count = 4`, both conclude "under threshold," and both auto-approve — landing the user at 6 active businesses with zero queued requests, silently exceeding the limit decision 4 exists to enforce. Given this product's actual concurrency (one or two people, occasionally two browser tabs), the practical risk is low, but it is worth doing properly since the rest of this codebase does: either serialize the count-and-insert inside one transaction at `SERIALIZABLE` isolation (Postgres will then abort the loser with a serialization failure, caught and retried or mapped to the pending path), or add a real DB constraint that can enforce a *count* rather than a boolean (harder — Postgres has no native "at most N rows matching a predicate" constraint the way a partial unique index gives "at most 1"). ### Phase 3 — business switcher

**Modify — client**
- `web/src/lib/api.ts` — **the design's "one place" claim (§8.1) is incomplete, and the gap is architectural, not just a missed line.** `request()` (line 56) is one fetch call site; `requestBlob()` (line 90, `getBlob`'s implementation) builds its own header object independently (`headers: { Authorization: ... }` only, no shared header-building code with `request()`). Both need the `X-Business-Id` injection, or every attachment download (photos, receipts — `PhotoCapture`, condition handovers, incident evidence) silently loses business scoping on the wire the moment this ships, even though the server would still enforce it correctly by session (Phase 1's middleware doesn't depend on this header working right for security — see §4 below — but a wrong/missing header on a multi-membership account could still misresolve which business's photo comes back on a client sending no header while `authMiddleware`'s step 4 falls through to `BUSINESS_NOT_SELECTED`, breaking the download rather than corrupting it. Still: fix both call sites, not one).

  **The deeper gap, found by tracing where `apiClient` itself comes from:** `createApiClient(baseUrl, getToken)` is called exactly once, in `web/src/main.tsx:52`, before React even mounts and before any business-selection state exists. `getToken`'s type (`TokenGetter = () => Promise<string>`, `api.ts:9`) is the precedent the design's "same injection shape" line (§8.1) refers to — but `request()`'s closure only captures that one getter, and there is no equivalent parameter for a business id today. Adding the header is not "one line inside `request()`" — it requires threading a second getter (the same shape: a function read fresh on every call, e.g. `() => string | null` reading `localStorage` directly, never a value captured at construction time) through `createApiClient`'s signature, into both `request()` and `requestBlob()`. Worth stating explicitly in whatever ships this, since "add the header" undersells the change to this file.

  **`/api/me`'s response is consumed in more places than `FirstRunGate`, found independently this pass:** `packages/shared/src/schemas/me.ts:14-19` and `api/src/handlers/me.ts:6-21` both return exactly one `businessId`/`role`/`driverId`, cached under the single un-parameterized key `["me"]`, and read synchronously — not just by `FirstRunGate` — in `web/src/lib/useMe.ts`, `web/src/components/Can.tsx:27` (every capability gate in the client goes through this), and `web/src/features/reports/ReportsCatalogueScreen.tsx:90`. **Checked against the design's own "hard remount, not `invalidateQueries`" policy (§8.1) and found sufficient**: because a switch is a full `queryClient.clear()` plus remount rather than a targeted invalidation, there is no window where `Can`/`ReportsCatalogueScreen` render against a stale cached role from the previous business — the remount is what closes exactly this gap. Recorded here so the next reader doesn't have to re-derive that the hard-remount requirement (already stated in the design) is the thing that makes this safe, rather than assuming it needs a separate fix.

  **A concrete example of the general risk the design already names, worth citing directly:** `web/src/features/review/ReviewMoneyScreen.tsx:37` and `web/src/features/review/ReviewThisMonthScreen.tsx:119` both key on `["partner", me.userId]` — a **user**-id key, not a business-id key, for an actual money figure. If the same person is a partner in two businesses, this is the literal case the design's §8.1 warns about in the abstract ("business A's money renders under business B's name"). `queryClient.clear()` on switch is already the correct, sufficient fix — this is not a new gap — but it is the concrete instance worth naming as the regression test (§5).
- `web/src/main.tsx` — `QueryCache.onError`'s existing 403 branch (line 41-45, confirmed as the only branch today) gains the `BUSINESS_NOT_SELECTED` branch.
- New: a business-switcher `Sheet` component, modelled on `MoreScreen`'s sign-out confirm (design correctly identifies this as the pattern to copy; confirmed `MoreScreen.tsx` exists and uses `Sheet` for a reversible confirm, consistent with UI §6.1's Sheet-vs-Dialog rule cited in the design).
- `localStorage` usage — **new to this codebase.** Grepped the full client tree; there is no existing `localStorage` call anywhere in `web/src`. The design's §8.1 ("selection persisted in `localStorage`") is the first use of browser storage in this client, which means there is no existing convention to match for the key name, no existing clear-on-sign-out hook to extend, and no existing test pattern for it. Needs: a key name decided now rather than improvised at write time (suggest `fleetsettle.selectedBusinessId`, namespaced against the stub-auth/e2e path never colliding with a real key), and explicit clearing on sign-out (`AuthGate`'s or the stub `signOut`'s responsibility — neither currently touches storage, since there was never anything to clear).

## 3. Data isolation — verified guarantees and residual gaps

The design's §4 states the hard boundary correctly and the enforcement mechanism (separate middleware, separate query directory, a forbidden-import guard, a separate audit table) is sound in principle. This section checks it against what actually exists today, table by table.

**Business-to-business isolation (Phase 1/3), what is verified:**

| Guarantee | Mechanism | Verified how |
|---|---|---|
| A business id never comes from client-supplied data | `check-forbidden.mjs`'s `tenancy/from-request` rule, extended (§2, Phase 1) to cover header reads too | Read the rule; confirmed it does not yet match `c.req.header`, confirmed the design's extension closes exactly that gap |
| A business not in the resolved membership set is unreachable | `authMiddleware` step 3, 404 not 403 | Read `middleware/auth.ts` in full; today's single-membership version already does this (`resolveMembership` returns `null` → `NotFoundError`), and the five-step rewrite preserves the same 404-for-absence shape for the header case |
| Stale client cache cannot show business A's data under business B's name | `queryClient.clear()` on switch | Grepped all 203 `queryKey` sites in `web/src`; confirmed none contains a business id anywhere, which is exactly what makes `invalidateQueries` insufficient and `clear()` necessary — the design's own reasoning, independently confirmed rather than taken on faith. Concrete instance found: `["partner", me.userId]` (`ReviewMoneyScreen.tsx:37`, `ReviewThisMonthScreen.tsx:119`) is a real money figure keyed on user id alone — exactly what `clear()` exists to protect, and the citation to use for the regression test (§5) |
| A linked driver's isolation (W-49) is unaffected by multi-membership | `driverId` in `Env.Variables` is set from the *selected* membership only, per-request | Confirmed `Variables.driverId` (`api/src/types.ts`) is singular and request-scoped already; the rewrite in `resolveMemberships` returning an array doesn't change how `authMiddleware` sets it — it still picks one membership (the one matching the header, or the sole one) and sets singular fields from it, same as today |

**Business-to-business isolation, residual gap found this pass:**

- `requestBlob`/`getBlob` not carrying the header (§2, Phase 3) — the server-side check is what actually matters for security (business scoping happens in the query, not the header), so this is not a data-isolation hole by itself, but it is a **correctness** hole: a multi-membership user's attachment fetch could 400 (`BUSINESS_NOT_SELECTED`) unpredictably depending on which fetch path a given screen happens to use, which is confusing at best and, if some future code path trusts the header's presence as *proof* of which business a blob belongs to rather than re-deriving it server-side, could become a real isolation bug later. Fix both call sites now while the difference between them is fresh, not after a second one is added.

**Platform-admin-to-money isolation (Phase 2), what is verified:**

| Guarantee | Mechanism | Verified how |
|---|---|---|
| Admin routes have no `businessId` in scope | `platformAdminMiddleware` (new) never calls `resolveMembership`/`resolveMemberships`, mounted at `/api/admin/*` instead of behind `authMiddleware` | Confirmed by reading `index.ts`'s mounting pattern — every existing route pairs a path with exactly one auth middleware; there is no existing path that runs both, so there is no precedent for accidentally composing them, and none should be added |
| Platform queries cannot import money-table schema | New `check-forbidden.mjs` rule scoped to `api/src/queries/platform/` | Not yet written (§2 flags the existing `isDomainOrQueries` helper is the wrong shape to reuse — it is an *exemption* for a different rule, not a *scope* for a new one). **This is the one enforcement mechanism in the whole isolation story that does not exist in any form yet and needs to be written new, not adapted.** Treat it as Phase 2's first task, same spirit as CLAUDE.md's "apply the DDL as `0001`, then `audit_log` as `0002`, before any money table holds live data" — write the guard before writing the first platform query it's meant to constrain, so it has something to catch from day one rather than being bolted on after the fact once a violation is already merged |
| Platform actions don't corrupt or piggyback on `audit_log` | Separate `platform_audit_log` table, `audit_log.business_id` stays `NOT NULL` | Confirmed `audit_log.business_id NOT NULL` at `api/migrations/0001_initial_schema.sql:876` (design cites 875 — off by one, immaterial) |
| An admin who is also a business member gets no special access inside that business | Nothing — this is true by construction, not by an added check, since the two middlewares are entirely separate code paths and a `platform_admin` row plays no role anywhere in `resolveMemberships`/`authMiddleware`/`auth/policy.ts`'s matrix | Confirmed `auth/policy.ts`'s `Role`/`Capability` types have no platform concept anywhere in them; adding one would be the mistake, not the fix |

**One structural question the design doesn't fully close, worth deciding before Phase 2 starts writing code:** `business_creation_request` (design §6.1) carries `currency_code`/`timezone`/`name` — i.e., everything `createBusiness` needs to actually build the business on approval. That is correct and necessary. But it means the *request itself*, sitting in a table `platform_admin`-tier code can read, contains no money — good — but the **requester's identity and business name** are visible to every platform admin for every pending request, by design (decision 3 only forbids *money* data, not business names — confirmed against §4's table, which explicitly allows `business` — name, created, member count). This is consistent with the design's own stated boundary, not a bug — flagged only so it's recorded as a conscious choice next to the boundary table itself when this reaches `docs/`, since "the admin can see business names but never money" is a sentence someone will otherwise have to re-derive from the schema.

## 4. Sequencing recommendation for shipping, not just building

Given §1's finding, recommend against shipping Phase 1 to production/QA on its own with a gap before Phase 2 follows. Reasoning: once `one_active_business_per_user` is dropped and `resolveMemberships` returns multiple rows, the *only* thing stopping unlimited business creation is Phase 2's threshold check — there is no intermediate safe state where Phase 1 is live and Phase 2 isn't. If these are separate PRs for review clarity (recommended — Phase 1 is infrastructure, Phase 2 is product behaviour, and reviewing them together makes the diff harder to read), merge them back-to-back and deploy together, or gate Phase 2's migration behind the same merge as Phase 1's rather than letting `develop` sit in the intermediate state for any length of time (recall: QA migrates automatically on every push to `develop` — DEPLOYMENT.md — so "intermediate state" here means minutes, not a deliberate soak period, but it's still worth not leaving to chance).

Track A (the claims fix) has no such coupling and can genuinely ship first and alone, as the design already states — confirmed nothing in Phase 1/2/3 depends on Track A beyond wanting real names to display, which is a UX nicety, not a correctness dependency the way Phase 1→2 is.

## 5. Testing — additions to the design's §10

The design's test list (§10) is sound; these are additions found by reading the test support code it would run against, not disagreements with it.

- **`api/tests/support/auth.ts` needs the new helper before Track C's own first listed test can be written** — see §2, Phase 1. Write the helper as part of Phase 1, not as a side effect of writing the first test that needs it, since Phase 2's tests will want it too (an admin who is also a member of two businesses).
- **The threshold race condition (§2, Phase 2)** deserves its own test: two concurrent `POST /api/business` calls from a user at their 4th active ownership; assert exactly one succeeds outright and the other either queues or fails cleanly, never both succeeding.
- **`getBlob` needs the same header-injection test `request()` gets** once both call sites in `web/src/lib/api.ts` carry the fix (§2, Phase 3) — otherwise a regression in one and not the other is invisible until an attachment silently 400s for a multi-membership user.
- **The new `check-forbidden.mjs` platform-query rule needs a fixture violation to prove it fires** — the existing test convention for these rules (confirmed by reading `scripts/check-forbidden.mjs`'s structure — every rule is a pattern plus a message, tested by construction rather than a dedicated test file for the guard script itself, as far as this pass found) should be followed rather than inventing a new verification style for just this one rule.
- **A regression test naming `["partner", userId]` directly** (§3): a partner in two businesses switches, and business A's partner-summary figures must not render under business B — this is the one concrete, already-existing money-bearing query key an independent sweep found that would actually collide without the `clear()` policy, so it is the test that proves the policy rather than just asserting the policy exists in the abstract.
- **`web/e2e/smoke.spec.ts:14` mocks `/api/me` at the network layer with today's singular shape** (`{ userId, businessId, role }`), confirmed across all four smoke tests. This suite will keep passing against a changed real response contract, because it never exercises the real one — it is testing its own mock. Update the mock in lockstep with the schema change, and treat continued e2e-green as no signal at all for this specific contract until it is.
- **Confirmed, not a gap: the offline mutation queue (M-12/P12) does not exist in code yet.** `web/vite.config.ts:44-48` explicitly defers runtime-caching/mutation-queue strategy to P12; there is no `persistQueryClient` or paused-mutation code anywhere in `web/src` today. Recorded so a future reader doesn't go looking for a queue to business-tag — there is nothing to retrofit. Whoever builds P12 later needs to tag queued mutations with the business id active when they were queued, not the one active when they replay; noted here only as a forward pointer.

## 6. Open questions this pass adds

Numbered to continue the design doc's own §12 list (currently five items) rather than restart numbering — see the corresponding edit to that document.

6. **Should Phase 1 and Phase 2 ship as one deploy or two adjacent ones?** §4 above recommends adjacent-but-inseparable; this is a judgement call about PR review size versus the intermediate-state risk, not a technical question with one right answer.
7. **What replaces the removed `one_active_business_per_user` catch in `createBusiness`/`redeemInvite`?** Simplest answer: nothing — let a genuine DB error surface as a 500 for the vanishingly rare case Phase 2's threshold logic didn't already catch, since the constraint that made a clean 409 possible is exactly what's being removed. Needs an explicit decision, not a silent "delete the dead branch and move on," because it changes what a caller sees on the one failure mode this pattern used to handle cleanly.
8. **Does the threshold race (§2, Phase 2) get the `SERIALIZABLE`-transaction fix, or is it accepted as a known, low-probability, low-harm gap?** Given the product's real concurrency (one or two people), accepting it explicitly and recording why may be the right call — but it should be a recorded decision, not an oversight, per this repository's own "record what you did not take" convention.
9. **`localStorage` key naming and sign-out clearing** (§2, Phase 3) — the design doesn't specify a key, and there's no existing convention in this client to inherit. Needs a name and an explicit owner for clearing it on sign-out before the first PR touching this lands, not decided ad hoc inside that PR.
10. **Does `BusinessAlreadyExistsError` get retired outright, or narrowed and kept?** Its own doc comment (`api/src/errors/app-error.ts:72-80`) asserts the very thing this design changes. If some code path still legitimately wants "you're already a member of this exact business" (e.g. redeeming an invite to a business you already belong to — `business_member_active_pair` still enforces this, unlike the dropped global index), the class may be worth keeping with a narrower comment rather than deleting; if not, retire it and its now-unreachable error code. Either way, `web/src/features/setup/CreateBusinessForm.test.tsx:60,66` (hard-coding its exact message) needs rewriting regardless of which way this goes.
11. **`api.ts`'s business-id getter — same shape as `TokenGetter`, or folded into it?** The architectural gap in §2/Phase 3 (no dynamic per-request business id in `createApiClient` today) can be closed either by a second parallel getter (`() => string | null`, mirroring `TokenGetter`'s shape) or by widening the existing token-getter contract to also resolve the business id in one call. The former keeps `web/src/lib/auth-asgardeo.ts` and `auth-stub.ts` untouched; the latter is one function instead of two threaded through `main.tsx`. Either works; pick one before writing `request()`'s new signature rather than discovering the seam mid-implementation.
12. **Does `platform_admin`'s grant/revoke get a DB trigger into `platform_audit_log`, matching `business_member_audit`'s precedent, or is an explicit application-level write acceptable?** `business_member`'s own grant/revoke/role-change history is doubly safe: two physical rows (never an in-place `UPDATE` — Plan.md's A11) *and* a trigger (`business_member_audit`, migration `0010`) that "cannot be forgotten in a new code path," in the exact words migration `0002`'s own header comment uses to justify triggers over application code everywhere else in this schema. `platform_admin` (§6.1) can't use the two-row trick — its primary key is `user_id` itself (correctly modelled on `business_settings`'s precedent, open question 12 above confirms this is sound), so a re-grant after a revoke is necessarily an in-place `UPDATE` on the one row that can exist for that user (the PK shape itself is fine — see the design doc's §14 note on the `business_settings` precedent — this finding is about the audit trail that shape implies, not the shape itself). §5 says "every change lands in `platform_audit_log`," but doesn't say by what mechanism — if that's an explicit `INSERT` written by hand in each domain function (`grantAdmin`/`revokeAdmin`), it is exactly the "developer remembered" pattern this codebase distrusts everywhere else, and a future admin endpoint added without going through those two functions would silently produce no audit trail. A generic trigger can't be reused as-is (`write_audit_log()` requires `business_id`, which `platform_admin` has none of, and can't compute `self_action` — that needs the acting admin's own id compared against the row being changed, business logic no generic before/after diff performs), but a small purpose-built trigger following the same shape is worth considering, or the explicit-write choice should at least be a recorded decision rather than an implicit one.
