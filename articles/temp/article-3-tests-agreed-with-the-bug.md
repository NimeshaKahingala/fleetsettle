# 386 passing tests, and the bug was in the path none of them took

*Post 3 of 3 — What the agent didn't write*

Two posts ago I described rationale-shaped code: an agent writing a comment that correctly explains why a row needs locking, above code that doesn't lock it. Last post: three of my four automated reviewers couldn't see that class of bug at all, because they read text, and the defect was an absence.

That leaves the defence every engineer actually trusts. I had 1,867 tests, 850 of them hitting a real Postgres database. No mocks anywhere near the schema, because in a money system most of the correctness lives in the constraints and a mock has none of them.

Here's the bug they missed.

## The role with no screen

The signup endpoint was assigning every newly created account a role that had no interface behind it. Sign up, land in the app, see nothing. About as visible a defect as a product can have.

It sat behind 386 passing integration tests.

The reason is worth sitting with, because I don't think it's specific to my project. Every test in that suite created its user through a helper that took the role as an argument — `mintUser(db, ctx, business, "manager")`. That's a sensible helper. I'd have written it. The agent wrote hundreds of tests with it, and every one of them worked perfectly.

But it means **no test in the entire codebase ever exercised what a real signup actually assigns.** They all told the system what role to use, then verified the system used it. Not one read back what the system decided on its own.

And then the part that still bothers me. One test *did* call the real signup endpoint — a happy-path test, written alongside the code. It asserted the role the endpoint returned. It asserted the wrong one as correct.

The test wasn't missing. It was **pinned to the bug**.

## The test that passed because nothing was listening

Second one, different shape, same lesson.

I'd written an accessibility check that failed a build if the browser emitted a specific console warning during a component interaction. It passed cleanly. It kept passing cleanly against code I already knew was broken, because I'd reproduced the violation by hand.

Headless Chromium builds the accessibility tree lazily. With no client asking for it, the check that produces that warning never runs, so the warning is never emitted, so a test asserting its absence passes — permanently, silently, and in the reassuring direction.

The fix was one line. The habit that caught it is the part worth keeping: **before you trust a test that asserts the absence of something, make it fail on purpose.** Fire the exact condition by hand and watch it go red. If it doesn't, you don't have a test, you have a green light wired to nothing.

I found a third instance later — a test asserting a particular label was correct for a figure the server deliberately doesn't attribute to anyone. It encoded the assumption instead of checking it, and it'd been green for weeks.

## The actual problem: the defences stopped being independent

Defence in depth works because failures are uncorrelated. The guard catches what review misses, review catches what tests miss, and the odds of all three failing on the same defect are small.

That reasoning quietly stops holding in agentic development.

The guard matches text patterns, so it can only see wrongness that is present. Three of my four reviewers read text, so they can only see wrongness that is present. And the tests — the tests were written by the same author as the code, in the same session, out of the same understanding.

**A test written by the author of the code doesn't verify the code. It restates it.** When the author was a human that was still mostly true and we papered over it with code review by a second human. When the author is an agent producing hundreds of tests per session, the correlation is total, and the volume makes it look like the opposite. 386 green tests reads as robustness. It was 386 restatements of one assumption.

## What I changed

Four things, all cheap:

1. **For every provisioning or setup path, one test that reads back what the system decided** rather than passing the value in and confirming it came out. The distinguishing question is: could this test still pass if the endpoint's own logic were replaced with the constant I gave it?
2. **Any test asserting an absence must be shown failing before it counts.** Make it red on purpose, once, in front of you.
3. **At least one reviewer in the stack that simulates execution**, not just reads the diff. Text reviewers are structurally incapable of the missing-line defect class.
4. **Treat a confident comment as a claim to verify, not as context.** With an agent, the comment is generated by the same process as the code and carries no independent evidence that the code does what it says. Read the delta between what the comment promises and what the code performs. That single habit found more real bugs for me than any tool.

## Would I do it again

Yes, and without much hesitation. One month, around 90,000 lines, one engineer, a system now live and handling real money. That is not a pace I can reach any other way, and none of the above is an argument against agentic development.

It's an argument against importing our old intuitions about what "reviewed" and "tested" mean. Those words used to imply independence. They don't any more, and the volume is very good at hiding it.

The agent will write you the reason. Checking that it also wrote the line is still your job.
