## S1 — the deposit repair needed its own review

**Use:** article 1's main story. **Evidence:** PR discussion, merged source, regression-test source; historical database and red/green results are reported in the discussion, not rerun here.

The initial repair in PR #176 treated refunded-but-held deposits as residue from test-data insertion. A review observation pointed to the opening-balance correction path instead. The response records checking QA's posting relationships and finding that ordinary corrections produced the rows. Repairing existing data without fixing that writer would let the new unique index break the next correction.

The writer fix then needed another correction: refunding the original opening-balance amount does not necessarily empty a deposit that was later topped up. Copilot flagged both the writer and the repair predicate. The resulting code checks the remaining balance before changing status; the topped-up correction is refused and rolled back rather than hiding held funds.

## S2 — two reviewers caught the same error-handling problem

**Use:** article 2. **Evidence:** two direct comments and the merged implementation.

Claude and Copilot both challenged mapping every `TypeError` to a validation response. Searching for explicit `throw new TypeError` statements did not account for errors thrown by the JavaScript engine itself. The broad mapping could classify programming failures as caller errors and suppress their error-level stack logging. A dedicated `WireFormatError` narrowed the mapping.

## S5 — residual issues are not completed-fix stories

**Use:** article 4 as a carefully qualified follow-up, only after checking later disposition. **Evidence:** source-inspected mechanisms, not newly executed reproductions.

The [logical audit](../../docs/evaluations/LOGICAL-ISSUES-AUDIT-2026-09-02.md) lists 14 findings. This editorial pass did not independently reproduce or endorse the severity of all 14. Two important mechanisms remain in the inspected code:

- The generic deposit movement path calculates a remaining balance but maps `refunded` to `released` without using it to enforce a full refund ([source](https://github.com/NimeshaKahingala/fleetsettle/blob/a5d19a3302cf979f9a94d283f3ea4dd59ed4cc2e/api/src/domain/deposit.ts#L252-L261)). This is distinct from S1's corrected opening-balance path.
- Recovery receipt reads `recovery.paymentId` before its transaction and later uses that captured value to decide reversal ([read](https://github.com/NimeshaKahingala/fleetsettle/blob/a5d19a3302cf979f9a94d283f3ea4dd59ed4cc2e/api/src/domain/incident.ts#L432-L440), [use](https://github.com/NimeshaKahingala/fleetsettle/blob/a5d19a3302cf979f9a94d283f3ea4dd59ed4cc2e/api/src/domain/incident.ts#L565-L566)). The transaction's UPDATE can serialize the writers while leaving the earlier value stale. It remains a concurrency defect; do not repeat the validation's categorical wording that it is “not a true concurrent race.” Locking a write does not retroactively refresh an earlier read.

These support a review question—has the invariant been checked across all writers?—not a claim that the entire defect family is now closed. Technical triage and remediation stay in the project workflow, outside these article plans.
