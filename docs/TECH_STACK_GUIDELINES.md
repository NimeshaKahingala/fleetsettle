# Implementation Guidelines

**Status:** v1.1 — auth confirmed, §1.2 closed
**Date:** 31 July 2026
**Companions:** `TECH_STACK.md` (the stack) · `DATA_MODEL.md` (the schema) · `UI_UX_GUIDELINES.md` (the client) · `user-flows-v1.md` (the behaviour)

**This document is downstream of `TECH_STACK.md`.** That document decides *what* the stack is; this one decides *how* to build on it — layering, error shape, transactions, testing, CI. Where the two disagree, `TECH_STACK.md` wins and this document is wrong.

**Provenance, because it matters for how you read this.** The first draft was a blueprint imported from a different codebase on a neighbouring stack. Most of its architecture — the acyclic layer rule, the error hierarchy, the integration harness, the CI gate — is genuinely good and is kept. But it specified a **different database driver, a different auth provider, a different money type and a different tenancy key** from the ones FleetSettle has already settled. §1 records every one of those conflicts and how it was resolved, so nobody re-opens a decision by reading a stale paragraph.

## 1. Conflicts with the settled stack, and how each was resolved

Seven, **all now settled.** Six are decided by `TECH_STACK.md`, and one is resolved in the imported document's favour. §1.2 was the last one open; it was confirmed on 31 July 2026.

| # | Imported guidance | FleetSettle | Resolution |
|---|---|---|---|
| 1 | Cloudflare **Hyperdrive** + Postgres.js over TCP | `@neondatabase/serverless` — `neon()` HTTP for reads, `Pool` WebSocket for writes (TS §3) | **Keep the Neon driver.** §1.1 |
| 2 | **Neon Auth** (Managed Better Auth), EdDSA | **Asgardeo** OIDC, verified with `jose` (TS §2) | **Asgardeo — confirmed 31 July 2026.** §1.2 |
| 3 | Money as `NUMERIC(12,2)`, string at the boundary | Money as **`bigint` minor units** (INV-20, TS §6) | Imported guidance is simply wrong here. §1.3 |
| 4 | Tenancy keyed by `user_id`, composite FKs to `users` | Tenancy keyed by **`business_id`**, resolved from `business_member` (TS §2, W-39) | Same technique, different key. §1.4 |
| 5 | Frontend: hand-rolled `fetch`, **no React Query** | **TanStack Query**, because the offline mutation queue depends on it (UI §12.1, M-12) | Keep TanStack Query. §1.5 |
| 6 | React 18 · React Router 6 | React 19 · TanStack Router (UI §12.1) | Superseded by the UI document |
| 7 | Migrations generated by the query layer | **Raw SQL migrations**, forward-only | Resolved in the imported document's favour. §1.6 |

### 1.1 Why not Hyperdrive

The imported document is right that Hyperdrive and `@neondatabase/serverless` are mutually exclusive — Hyperdrive is a TCP pooler, the Neon driver deliberately speaks HTTP and WebSockets. It is the *conclusion* that does not transfer.

| Hyperdrive gives you | Worth it here? |
|---|---|
| Global connection pooling | **No.** TS §1 sizes this app at a handful of users with long idle stretches. There is no connection pressure to relieve |
| Edge query caching (60s default) | **No, actively harmful.** It requires the two-binding cached/uncached split, and on a ledger the wrong binding on one query means a manager watching a payment he just recorded vanish. That is a correctness bug traded for latency this app does not need |
| Lower cold-connection latency | Marginal, and the HTTP driver has no connection to establish for the read path at all |

And it costs something specific: FleetSettle's writes are transactional by nature — recording a payment writes the receipt, its allocations, the obligation status and the audit row in one transaction (TS §3). Hyperdrive's own guidance is against holding multi-statement transactions on a pooled connection, which is most of this application's write path.

**Decision: keep `neon()` + `Pool`.** Revisit only if read traffic grows enough to want edge caching, at which point Hyperdrive can front the *read* path alone.

### 1.2 Auth — settled: Asgardeo

`TECH_STACK.md` §2 and §8 specify Asgardeo, and the imported blueprint proposed Neon Auth in its place. **Asgardeo confirmed, 31 July 2026.** Both would have worked; the trade was real and is recorded here so it is not re-litigated from a stale draft.

| | **Asgardeo** — chosen | **Neon Auth** — not chosen |
|---|---|---|
| Status | Generally available | **Beta.** API surface not frozen |
| Where users live | External IdP | `neon_auth` schema in your own database |
| Region constraint | None | **AWS only**; incompatible with Neon IP Allow and Private Networking |
| Token | RSA JWT, ~1h | EdDSA, 15 min, refresh handled by the client library |
| Custom claims | Yes | No — irrelevant either way, since authorisation lives in `business_member` (TS §2) |

**Why Asgardeo.** A ledger whose whole promise is being believed about money is a poor place to depend on a beta identity service, and the decision was already documented with its bindings written down. Neon Auth's genuine advantage — one less vendor and a simpler client — buys a convenience whose cost is a dependency that can change under you.

**What the alternative would have bought, stated plainly** so nobody thinks it was dismissed cheaply: fewer moving parts, no second dashboard, JWKS handled for you, and users living in the same database as everything else. If Asgardeo becomes a burden in operation rather than in theory, that is the reason to revisit — not the token lifetime, which is not a real problem (§7.3).

**What is now closed by this.** The client library is `@asgardeo/auth-react` ^5.6.2, the Worker verifies with `jose` against Asgardeo's JWKS cached in KV, and the four rules in §7.1 are fixed. `ASGARDEO_ISSUER`, `ASGARDEO_JWKS_URL` and `ASGARDEO_AUDIENCE` are the bindings (TS §8).

*If it is ever reversed*, three things change and nothing else: the JWKS algorithm (`EdDSA`, not RSA), the token lifetime, and the client config. The `sub → app_user → business_member` resolution is provider-independent by design, which is what keeps the reversal cheap.

### 1.3 Money is `bigint`, not `NUMERIC`

The imported §5.7 discusses `NUMERIC` arriving as a string and recommends keeping money as strings end to end. FleetSettle already settled a stricter rule and it supersedes that entirely:

> Money is a `bigint` in domain code, a `string` on the wire, and never a `number` anywhere. — TS §6

So a Zod row schema for a money column is `z.string()` (the wire shape), parsed to `bigint` at the domain boundary by one codec. See §5.4.

### 1.4 Tenancy is `business_id`

The composite-FK technique from the imported §6 is excellent and is kept — it makes cross-tenant row grafting structurally impossible rather than guarded against in code. Only the key changes: **`business_id`, never `user_id`**, resolved from the verified `sub` via `business_member` and never taken from a request body (TS §2, rule 1).

The linked-driver boundary is stricter still and is a security requirement, not a preference (W-49): a driver's token must not reach another driver's row by any route, including a report or an export. That is `driver_id` scoping in the data layer, not a claim to be trusted.

### 1.5 Why TanStack Query, against the imported advice

The imported document argues a ~100-line typed `fetch` wrapper beats React Query, and for that codebase it probably did. It does not here, for one reason: **M-12 requires writes to survive being offline.** TanStack Query's paused-and-persisted mutations are that mechanism — a hand-rolled wrapper would have to reimplement a durable mutation queue, replay, and rollback, which is materially more than 100 lines and is exactly the code you do not want to own on a money app.

What *is* worth keeping from the imported wrapper: dependency inversion for the token getter (§7.3), `fieldErrors` extraction onto form fields, and the 401-retry-once backstop. All three sit underneath TanStack Query rather than instead of it.

### 1.6 Raw SQL migrations, Drizzle for queries only

`TECH_STACK.md` §1 picks Drizzle and mentions "migrations in-repo". Sharpening that, because `DATA_MODEL.md` forces the issue: the schema leans on **exclusion constraints, partial unique indexes, deferred constraints, triggers and rules** (TS §7). A schema-diffing migration generator does not reliably round-trip those, and a money schema where the enforcement silently fails to migrate is the worst possible failure.

**So: migrations are hand-written SQL, numbered, forward-only. Drizzle is the typed query layer and its schema file mirrors the DDL rather than generating it.** The DDL in `DATA_MODEL.md` §16.0 already executed against Postgres 17 — that is migration `0001`, near enough verbatim.

```
/
├── api/                        Cloudflare Worker
│   ├── src/                    §3
│   ├── migrations/             NNNN_description.sql, filename order, forward-only
│   ├── scripts/migrate.ts      tsx, runs in Node — not in the Worker
│   ├── tests/{unit,integration,support}/
│   └── wrangler.jsonc
├── web/                        Vite SPA — see UI_UX_GUIDELINES.md §12.2
├── packages/shared/            Zod schemas + the money codec, imported by both
├── docs/
├── .github/workflows/
└── package.json                npm workspaces
```

**`packages/shared` is not optional here.** The money codec must be byte-identical on both sides (§5.4), and the client's Zod schemas must be the same objects the Worker validates with — hand-mirrored types drift silently, and the thing that drifts is a money field.

**Root scripts delegate, never implement:** `npm run lint` → `npm run lint --workspaces --if-present`. CI and humans use the same entry points.

## 3. Backend architecture

### 3.1 The layer rule

Imports only ever point downward:

```
src/constants/     literal tuples, enums, tunable defaults
src/schemas/       Zod per resource                → constants
src/db/            client.ts, schema.ts, migrations
src/queries/       pure SQL/Drizzle per resource   → schemas + Db type
src/domain/        one module per flow group (F-2 leases, F-4 daily, …)
src/auth/          verify.ts (jose), policy.ts (W-49 capabilities)
src/route-defs/    createRoute() objects           → schemas
src/handlers/      handler functions               → import type route-defs
src/routes/        wiring only
src/errors/        AppError hierarchy
```

Handlers import route-defs with `import type` so the import is erased and no runtime cycle forms.

`domain/` is the one addition to the imported structure, and it exists because FleetSettle's write paths are not CRUD. "Confirm the day" is four inserts, a state transition and an audit row, in one transaction (F-4.2). That belongs in a named module with a test, not inline in a handler.

### 3.2 Adding an endpoint — the fixed order

1. `constants/` — literal tuples, if any
2. `schemas/<resource>.ts` — request, response, DB row. Money fields are `z.string()`
3. `queries/<resource>.ts` — `async (db: Db, …)`. No Hono, no `c`, no auth
4. `domain/<flow>.ts` — if the write is more than one statement
5. `route-defs/<resource>.ts` — declare **every** status the handler can produce
6. `handlers/<resource>.ts` — read the business from `c.get("businessId")`, never the body
7. `routes/<resource>.ts` — wiring
8. Mount, test (§8), document

### 3.3 Errors

One `AppError` base, typed subclasses, one global `app.onError`. Handlers **throw**; they never hand-roll an error response.

```jsonc
{ "error": "Trip not found", "code": "NOT_FOUND", "requestId": "…", "details": [ /* optional */ ] }
```

| Situation | HTTP | `code` |
|---|---|---|
| Invalid input | 400 | `VALIDATION_ERROR` or domain-specific |
| No `Authorization` header | 401 | `MISSING_TOKEN` |
| Bad/expired JWT | 401 | `INVALID_TOKEN` |
| Row missing **or belonging to another business** | 404 | `NOT_FOUND` |
| Capability the role lacks (W-49) | 403 | `FORBIDDEN_CAPABILITY` |
| Invariant violation (INV-1 double-booking, INV-17 unreconciled advance) | 409 | domain-specific |
| Write into a closed accounting period | 409 | `PERIOD_CLOSED` |

**Cross-tenant access returns 404, never 403** — a 403 confirms the row exists.

**403 is correct for a capability, though**, and the distinction is deliberate: a manager who cannot write off a debt *knows* the debt exists, he simply may not do that to it. The client renders those two differently too — absent versus disabled-with-reason (UI §12.4, M-22).

**`PERIOD_CLOSED` deserves its own code** because the client's response to it is specific: the fact is not rejected, it posts to the open period carrying a reference to the one it belongs to (W-35). A generic 409 would leave the UI guessing.

### 3.4 Structured logging

One JSON object per line, so Workers Logs can parse it without a grok pattern: `level`, `requestId`, `method`, `path`, `status`, `duration`, `userId`, `businessId`, `timestamp`. `onError` emits the same shape at `error` (5xx, with `stack`) or `warn` (4xx). `requestId` is echoed in the response header and the error body, so a user-reported failure maps to a log line.

Never log a request body in production — these bodies contain NIC numbers, phone numbers and amounts.

```toml
[observability]
enabled = true
```

### 3.5 OpenAPI, gated in production

Routes are `createRoute()` objects, so the spec generates itself. Serve it at `/api/docs`, and **404 both the UI and the spec when `ENVIRONMENT === "production"`** — a public spec advertises the whole API surface. CI asserts the 404 as a production smoke check.

## 4. Data access

### 4.1 Two modes, chosen deliberately

Per TS §3:

```ts
// db/client.ts
import { neon, Pool } from "@neondatabase/serverless";

export const reader = (url: string) => neon(url);           // single-statement reads
export const writer = (url: string) => new Pool({ connectionString: url });
export type Db = ReturnType<typeof reader>;
```

| Mode | Use |
|---|---|
| `neon()` HTTP | Single-statement reads — reports, lists, lookups. One round trip, nothing to hold |
| `Pool` WebSocket | Anything writing more than one row. Interactive transactions |

**Close the pool in `ctx.waitUntil()`, never in the request path.** Never hold either in module scope across requests — isolates are reused, connections are not safe to share.

### 4.2 Transactions are the default for writes, not the exception

Most write paths here are multi-statement and must be all-or-nothing. F-4.2 — the most frequent operation in the product — is four inserts, and a partial write leaves a day confirmed but unpaid, which is a debt the driver does not owe.

```ts
const client = await pool.connect();
try {
  await client.query("BEGIN");
  // … day_record, obligation, payment, payment_allocation
  await client.query("COMMIT");
} catch (e) { await client.query("ROLLBACK"); throw e; }
finally { client.release(); }
```

Rules that follow from the schema rather than from taste:

- **Nothing loops over rows issuing queries.** Bulk operations use `insert … select` and `update … from` (TS §7). The bulk-confirm flow (F-4.6) is one statement per table, not one per day.
- **Aggregation happens in SQL, never in the Worker** — CPU time is bounded per invocation. The report queries in `DATA_MODEL.md` §15 are the implementations, not sketches.
- **A write into a closed period will be refused by a trigger**, not by your code (`assert_period_open()`). Catch it and map it to `PERIOD_CLOSED`; do not pre-check it in the application, because the pre-check and the trigger will eventually disagree.

### 4.3 Idempotency is a schema property

Cron jobs and retried mutations must not double-write, and the guarantee is in the constraints, not in code: `day_record` is unique on `(daily_lease_id, business_date)`, `billing_period` on `(lease_id, seq)`, `message` on `(trigger, subject, stage)` (TS §4). A duplicate run hits a constraint and stops.

Handle the unique violation as a **success** on those paths. A cron that fires twice should be a no-op, not a 500 and a page.

### 4.4 The money codec

```ts
// packages/shared/money.ts — imported by the Worker and the client
export type Minor = bigint;
export const parse  = (wire: string): Minor => BigInt(wire);
export const toWire = (v: Minor): string => v.toString();
```

`bigint` columns come back from the driver as **strings** and `JSON.stringify` cannot serialise a `BigInt`, so the boundary conversion is not optional. A money value that has passed through `Number` is a bug even when the arithmetic is right (TS §6).

Add a lint rule. This is the single easiest thing in the codebase to get wrong quietly.

### 4.5 Timezone

```ts
const businessDate = (tz: string) =>
  new Intl.DateTimeFormat("en-CA", { timeZone: tz }).format(new Date()); // YYYY-MM-DD
```

`new Date().toISOString().slice(0,10)` is wrong and will be off by one for five and a half hours a day (TS §5). The same rule applies in SQL: **pass the business date as a parameter, never `CURRENT_DATE`** — Postgres would evaluate it in the server's timezone. `DATA_MODEL.md` §15's ageing query does exactly this and says why.

Worth a lint rule too.

## 5. Database conventions

- **UUID v4 primary keys**, `DEFAULT gen_random_uuid()`. Never serial — ids appear in URLs and must not be enumerable.
- **Composite FKs for tenant isolation**, keyed on `business_id` (§1.4). The parent needs `UNIQUE (id, business_id)` for the child to reference the pair.
- **Money is `bigint` minor units.** Never `float`, never `numeric` for money in this schema.
- **`CHECK` constraints for every bounded value.** Zod is the fast path; the database is the truth. Both.
- **`created_at` / `updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`** plus the shared `trigger_set_updated_at()`.
- **Never drop or rename a column** without explicit instruction. Add and backfill.
- **A new money table is not finished until it is in the `assert_period_open()` trigger array.** `DATA_MODEL.md` §13 carries a CI assertion for exactly this, because the list is hand-maintained and drifted once already.

### Migrations

Numbered raw SQL, applied in filename order by a `tsx` runner, tracked in `_migrations`. Forward-only — a money system that rolls a migration backwards over live data has a worse problem than the migration.

Two hardening items from commit one, both cheap now and expensive later:

- **A Postgres advisory lock** around the run, so two concurrent deploys cannot both read an empty `_migrations` and both apply.
- **A SHA-256 checksum per filename**, so an already-applied file that is later edited fails loudly instead of being silently skipped.

## 6. Scheduled work

Everything the system does "without being asked" is a Cron Trigger (TS §4), and **all of it is idempotent** (§4.3).

| Job | Cadence |
|---|---|
| `generate-day-cards` | daily, early |
| `generate-billing-periods` | daily |
| `dispatch-messages` | every 15 min inside the send window |
| `paperwork-warnings` | daily |
| `deposit-hold-release` | daily |

**No cron is a prerequisite for a user action.** F-4.2 states the rule: confirming a day whose card was never generated creates it. The job is an optimisation. Build every cron-fed screen so that a job which failed overnight is invisible to the user, because the alternative is the most-used screen in the product going dark for a reason the manager can neither see nor fix.

## 7. Auth

### 7.1 The chain

```
React (@asgardeo/auth-react) ──login, PKCE, refresh──► Asgardeo
                                                          │ access token (JWT)
   Authorization: Bearer <jwt>                            ▼
Worker ─ jwtVerify(token, JWKS, { issuer, audience })   ← jose, JWKS cached in KV
       ─ payload.sub ──► app_user.asgardeo_sub
       ─ app_user.id ──► business_member (role, business_id)
       └ every query scoped by business_id
```

Four rules, all from TS §2 and none negotiable:

1. **`business_id` is never taken from the request body.** It is resolved from the verified `sub`. A client-supplied business id is the whole multi-tenancy bug in one line.
2. **The JWT is verified on every request.** There is nowhere in Workers to keep a session cheaply.
3. **JWKS is cached in KV** with a TTL and refetched on `kid` miss.
4. **A linked driver's token is the same shape as anyone else's.** The read-only boundary (INV-25) is enforced by `driver_id` scoping in the data layer, not by trusting a claim.

### 7.2 Capability checks live in one place

`auth/policy.ts`, one function per row of the W-49 matrix, called by handlers. The client has a copy for rendering (UI §12.4) and it is **convenience only** — every capability is re-checked here.

### 7.3 Do not build the refresh choreography

The imported document's longest warning is worth heeding in advance: single-flight refresh locks, proactive expiry checks, session rescue and `fetch` monkey-patches are the accumulated scar tissue of one IdP's rotating-refresh-token races. Start with the SDK's own refresh plus a **401-retry-once** backstop in the API client, and add nothing until a real failure justifies it.

## 8. Testing

### 8.1 Two Vitest projects

- **Unit** — pure functions only. The money codec, the business-date helper, allocation ordering, period arithmetic. No DB, no network.
- **Integration** — the real Hono app via `app.request()` against a **real Neon test branch**. Never mock the database; this schema's correctness is largely its constraints, and a mock has none of them.

### 8.2 The golden fixtures are the regression suite

`user-flows-v1.md` §9.1 encodes the three worked walkthroughs as fixtures with real figures. They are already proven against Postgres 17 (`DATA_MODEL.md` §16.1, 39 of 39 assertions).

**Any change that moves `134,000`, `15,000` or `7,500` is a breaking change and must fail loudly.** Seed a preview branch with them and assert in CI.

The seed walks the real period lifecycle — open July, write July, close July and open August — because there is no way to write into a closed period. So the fixtures exercise UC-98 as a side effect of testing the figures.

### 8.3 Support modules, built before the first endpoint

| File | Responsibility |
|---|---|
| `support/env.ts` | Parses `.dev.vars`; exports `TEST_ENV`, `TEST_DATABASE_URL` |
| `support/client.ts` | `app.request(path, init, TEST_ENV)` — full middleware chain, no server |
| `support/auth.ts` | Mocks the verifier; mints users in each W-49 role, including a linked driver |
| `support/factories.ts` | Business, vehicle, driver, lease, **an open accounting period**, and a cascade-safe cleanup |
| `support/fixtures.ts` | The §9.1 golden seeds |

The safety rail is non-negotiable:

```ts
if (!TEST_DATABASE_URL) throw new Error("TEST_DATABASE_URL is not set");
if (devUrl && TEST_DATABASE_URL === devUrl) throw new Error("TEST_DATABASE_URL must not equal DATABASE_URL");
```

**Every endpoint covers:** happy path · 401 missing header · 401 verifier throws · 403 role lacks the capability · 404 belongs to another business · 409 on its invariant, if it has one · `PERIOD_CLOSED` where a period is involved.

**And one test class specific to this product:** a **linked driver** must receive 404 for every route touching another driver's data, including reports and exports. W-49 calls that boundary a security requirement, and a security requirement without a test is a hope.

## 9. CI/CD

### 9.1 Environments

| Env | Git branch | Neon branch |
|---|---|---|
| Local | any | personal branch |
| Preview | any PR | ephemeral branch, seeded with §9.1 fixtures |
| Production | `main` | `main` |

### 9.2 The Neon free-plan constraints are load-bearing

`TECH_STACK.md` §10 records two limits that the branching strategy must respect, and both bite silently:

- **10 branches per project.** The per-PR preview branch needs a **delete-on-merge/close step**, or branch creation starts failing at around nine open PRs — and it fails in CI, on someone else's PR, for a reason that looks unrelated.
- **No protected branches.** Nothing at the platform level stops `main` being reset by a branch operation. That guardrail has to come from who holds Neon console access.

### 9.3 The gate

One reusable `checks.yml` called by every deploy workflow, so preview and production clear a bit-identical bar: `lint`, `typecheck`, unit tests, web tests, build. Integration tests run after migration against the seeded preview branch.

### 9.4 Deploy safety

```jsonc
// wrangler.jsonc
{
  "name": "fleetsettle-api-local",   // differs from every deployed Worker, so a bare
                                     // `wrangler deploy` can never overwrite production
  "workers_dev": false,
  "preview_urls": false
}
```

Secrets via `wrangler secret put`, never in `vars` — those are plaintext in the deployed bundle.

## 10. Security baseline

1. Every protected route verifies the JWT and scopes **every** query by `business_id` from the token.
2. **Never** trust `business_id`, `driver_id` or any owner id from a request body or query param.
3. Parameterised SQL exclusively. No string concatenation, ever.
4. Cross-tenant access returns 404; a lacked capability returns 403 (§3.3).
5. The linked-driver boundary is tested, not assumed (§8.3).
6. No request bodies in production logs — NICs, phone numbers, amounts.
7. `/api/docs` 404s in production, verified in CI.
8. Composite FKs make cross-business writes structurally impossible (§5).
9. Security headers on the assets Worker — CSP, HSTS, `X-Content-Type-Options`, `Referrer-Policy`. The highest value-to-effort item on this list.
10. R2 objects are served through **presigned, expiring URLs**, never a public bucket. Condition photos are evidence in disputes and often show number plates.

## 11. Day-one items

Each is cheap now and expensive to retrofit.

| | |
|---|---|
| **The `audit_log` writer** | `DATA_MODEL.md` D-8 — the table exists with no writer. A generic `AFTER INSERT OR UPDATE` trigger, built **before any money table holds live data**. An audit trail with a gap at the beginning is the stretch someone eventually needs |

| **Advisory-locked, checksummed migrations** | §5 |
| **`/api/ready`** that runs `SELECT 1` | `/api/health` returning `{ok}` without touching the database stays green through a total outage. Point the smoke check at `ready` |
| **Error monitoring** | Sentry or a Tail Worker. Structured logs nobody alerts on are forensics, not monitoring |
| **Preview-branch cleanup** | §9.2. Not optional on the free plan |

## 13. What not to build

- **A refresh-token state machine** (§7.3) until a real failure demands one.
- **Database-backed rate limiting.** Use the Workers rate-limiting binding; a token row per request is two round trips and unbounded growth.
- **A runtime `GET /api/config`.** Build-time env vars are enough and it puts a round trip in front of first paint.
- **An application-side period-open pre-check** (§4.2). The trigger is the truth; two implementations of one rule will diverge.
- **A reply inbox for WhatsApp.** W-45 put it out of scope deliberately; the number carries an auto-reply pointing at a phone.
- **Anything that reads a money column into a `number`** (§4.4).
