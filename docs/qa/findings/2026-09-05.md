## 3. Crediting lease days — F-2.4/UC-15 on a monthly rental

Business `TestBusinesByChamath`, vehicle `HB-0628`, Madura, Rs 930/month, billing day 3 — an ongoing arrangement-A lease with a real unpaid due.

**Navigation worth recording:** "Adjust or waive" is a *due* action, not a lease action. It is reached by tapping the due row itself under "Dues"; the "Lease actions" ⋮ menu offers only Renew / Read odometer / Close the lease. Only unpaid dues are tappable — a settled due renders as static text. This tripped up the walkthrough and will trip up a user.

Recorded `agreed_discount`, direction "Reduces what's owed", Rs 155. The due moved 930 → 775 while the **Billing periods** section below continued to read Rs 930 — which is W-25 rendered correctly on screen: the agreed rent is untouched, only what is owed this period moved.

Confirmed the type semantics against `domain/adjustment.ts` rather than inferring them from one observation: a `waiver`/`auto_waiver` leaves `amount_minor` standing and raises `waived_minor`, so both "the 930 charged" and "the 155 waived" survive; **every other type moves `amount_minor` directly**. Observed exactly that — `agreed_discount` wrote `amount_minor 93000 → 77500` with `waived_minor` unmoved at 0.

Separately confirmed from `queries/reports.ts:1840` that UC-77's goodwill report filters `adjustment_type IN ('waiver','auto_waiver','goodwill')` — so **`agreed_discount` never reaches the goodwill-given total**. This is correct by design (a negotiated price is not goodwill given) but it is a genuine fork in the user's hands with no on-screen explanation, and it is the single most important thing the guide had to say about this screen.

**Void reversal is exact.** A Rs 1 `goodwill` test entry voided with a reason put the due back 77400 → 77500 to the cent, and the row stayed visible in the adjustments sheet marked `· voided` with its Void button correctly gone.

## 4. GAP-216 — no odometer on a maintenance expense, so the service prompt can never fire

**Found while walking F-3.5, which specifies the field explicitly:** *"Steps — Same screen as F-3.1: amount, vehicle, category, date, odometer (optional)… **Writes** `Expense`, `OdometerReading?` when a reading is given."*

`RecordExpenseSheet.tsx` contains **zero** occurrences of "odometer". The level-2 disclosure offers Paid by, Borne by, Note and Photo, and nothing else. The backend is complete and unused: `domain/expense.ts` accepts `odometerReadingKm`/`odometerSource` and writes a real `odometer_reading` row inside the same transaction, with a comment citing GAP-30/F-3.3 as the reason it exists.

The consequence is not the missing field — it is what the missing field silently disables. `getVehicleMaintenanceStatus` (`domain/vehicles.ts:306`) compares the latest odometer reading against `findLastMaintenanceOdometerKm`, and that query (`queries/expense.ts:159`) **inner-joins `odometer_reading` through `expense.odometer_reading_id`**, filtered to `category = 'servicing'`. With no client path able to set that column, the join can never match, `lastMaintenanceKm` is always `undefined`, and the function returns `{ kmSinceLastServiceKm: null, due: false }` for every vehicle, forever.

So GAP-68's service-interval feature ships a settable interval (`SetServiceIntervalSheet.tsx` exists and works) and a prompt that is structurally unreachable.

Confirmed against live data rather than argued from source alone:

```
total expenses            20
with an odometer reading   0
servicing rows             0
servicing with odometer    0
```

Filed as **GAP-216** in `TRACKER.md` §4. Not fixed this session — the session's deliverable was the guide, and the guide carries a plain-language warning telling users to treat the Service interval setting as doing nothing and to diarise services themselves until this closes.

**Fixed in a follow-up session, same finding.** Planning the client-only odometer fix surfaced a second, independent cause: `SetServiceIntervalSheet.tsx` called `api.post` against `/{id}/service-interval`, a route registered **PATCH-only** — so the interval could never actually be saved against the real API, and this test's own mock (`post`, asserted on `post`) encoded the bug rather than catching it. Filed as **GAP-217**; both closed together on `fix/gap-216-217-service-reminder`. `RecordExpenseSheet.tsx` and `FuelFillSheet.tsx` both gain the odometer pair; `SetServiceIntervalSheet.tsx` moves to `api.patch`. Full account in `TRACKER.md` §4's GAP-216/GAP-217 rows.

## 5. Rejected: adjustment `reason` silently dropped

Worth writing up because it looked serious for several minutes and would have been a bad thing to report.

The first adjustment saved with `reason = NULL` in the database, despite the reason text being plainly visible in the sheet in the screenshot taken at save time. `NoteField` is a *controlled* textarea (`value={value}`), so a rendered value normally proves React state holds it — which pointed at the client dropping a field on a money record, exactly the kind of W-50 audit failure that matters.

It is not. `get_network_request` on the actual POST showed the request body carried no `reason` key at all:

```json
{"obligationId":"…","adjustmentType":"agreed_discount","amountMinor":"15500","sign":-1}
```

A controlled re-test settled it: filled the reason, then forced a re-render by changing the adjustment type, and the text **survived** the re-render — proving state genuinely held it that time — and the resulting POST carried `"reason":"Reason-persistence retest"` correctly, which the database then stored.

So the first miss was this tool's `fill()` setting the DOM value without React seeing the event, and the sheet being saved before any re-render could reveal that state was still empty. **A tool artifact, identical in shape to the one the 28 Aug pass hit on a native date input** — and the same artifact bit again on a date field this session, requiring a native-setter `evaluate_script` to set an end date. No app defect. The `reason` plumbing is correct end to end: schema (`z.string().trim().max(500).optional()`), domain (`insertAdjustment`), and query layer all carry it.

The one durable lesson, which the 28 Aug pass already recorded and this session re-learned the hard way: **after `fill()`, force a re-render and re-snapshot before trusting the value** — for a controlled React input, surviving a re-render is the only cheap proof that state, not just the DOM, holds what you typed.
