## GAP-191 (new) — incident bottom line doesn't refresh on void

After voiding the Rs 500 repair cost, the expense list correctly showed it struck through with the reason attached, but "Total repairs"/"Net cost to you" held at Rs 500 in the same browser tab. A hard reload (`ignoreCache`) then read Rs 0 correctly — proving the underlying data was always right, this is a stale-client-cache bug, not a miscalculation.

Root cause, confirmed by source rather than guessed: `IncidentScreen.tsx:392`'s void action passes `invalidateKeys={[["incident", incidentId, "expense"]]}` only. The incident *detail* query (`["incident", incidentId]`, which carries the server-computed `bottomLine.totalRepairsMinor`/`netCostMinor`) is invalidated elsewhere in the same screen only by the close-incident mutation (`:159`), never by voiding a cost. The trip side doesn't share this bug, but not from a parallel fix — `TripDetailScreen.tsx:138` computes "Costs so far" client-side by summing the trip's own (already-invalidated) expense list, so it happens to be immune.

This had zero visible surface before GAP-172 shipped (25 Aug) — GAP-172 is the first time a real cost could ever be attached to, and therefore voided from, an incident via the client. Filed as **GAP-191** in `TRACKER.md` §4.

## 5. GAP-186 — distributable cash report

Reports catalogue → "What can we safely take out" (present, `PiggyBank` icon). Four tiles: Cash on hand and in bank Rs 50,199.79, Held as deposits Rs 6,000, Loan instalments due Rs 0, Safe to take out Rs 44,199.79 — internally consistent (50,199.79 − 6,000 − 0 = 44,199.79 exactly).

Cross-checked `depositsHeldMinor` directly against Neon (`deposit`/`deposit_movement`, business `TESTA` = `019fd4c9-0360-7655-9e48-7451b488e818`): summing signed movements for deposits in `held`/`hold_window` status gives exactly Rs 6,000, matching the UI exactly. Cross-checking `cashOnHandMinor` itself proved more involved than a single query justifies in this pass: the real formula (`getDistributableCashReport`) sums per-partner held cash, banked-by-destination totals and deposits held, net of outstanding driver advances and banking-event discrepancies — a naive `sum(payment.amount_minor)` replica landed within Rs 200 of the true figure (44,399.79 vs the true 44,199.79-implied component), close enough to confirm deposits are clearly being folded in (the whole point of GAP-186's fix) but not an exact reconciliation. Not treated as a defect — the gap is consistent with the advance/banking-event nuance the naive query didn't model, not with the deposit-fold bug the fix actually addressed. A full reconciliation, if wanted, needs to replicate `listPartnerCashPositions`/`listBankedByDestination`/`sumInstalmentsDueForBusiness` exactly rather than approximate them.
