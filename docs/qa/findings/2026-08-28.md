## GAP-191 — incident bottom line doesn't refresh on void

After voiding the Rs 500 repair cost, the expense list correctly showed it struck through with the reason attached, but "Total repairs"/"Net cost to you" held at Rs 500 in the same browser tab. A hard reload (`ignoreCache`) then read Rs 0 correctly — proving the underlying data was always right, this is a stale-client-cache bug, not a miscalculation.

Root cause, confirmed by source rather than guessed: `IncidentScreen.tsx:392`'s void action passes `invalidateKeys={[["incident", incidentId, "expense"]]}` only. The incident *detail* query (`["incident", incidentId]`, which carries the server-computed `bottomLine.totalRepairCostMinor`/`netCostMinor`) is invalidated elsewhere in the same screen only by the close-incident mutation (`:159`), never by voiding a cost. The trip side doesn't share this bug, but not from a parallel fix — `TripDetailScreen.tsx:138` computes "Costs so far" client-side by summing the trip's own (already-invalidated) expense list, so it happens to be immune.

This had zero visible surface before GAP-172 shipped (25 Aug) — GAP-172 is the first time a real cost could ever be attached to, and therefore voided from, an incident via the client. Filed as **GAP-191** in `TRACKER.md` §4. **Fixed the same day** (PR #148): `invalidateKeys` now also carries `["incident", incidentId]`, with a regression test that fails against the pre-fix code and passes with it.

### Confirmed findings

#### GAP-196 — trip detail confuses payable and receivable (P1)

**Reproduction.** Close a trip that has both a customer fare and a driver fee. Pay the customer fare in full while leaving the driver fee unpaid. Re-open trip detail. The `Received` row renders `Due Rs 25` and opens `Collect payment`, even though the only Rs 25 due is money the business owes the driver. During this pass the live database held both obligations against the same trip source:

- `trip_fare`, `owed_to_us`, Rs 123.45, paid;
- `driver_fee`, `owed_by_us`, Rs 25, initially pending.

**Root cause.** `api/src/queries/obligation.ts:105` `findObligationBySource` filters only `source_type`, `source_id`, and `voided_at`, then returns one row. It does not constrain direction or kind. `api/src/handlers/trip.ts:229` calls that generic function and labels whichever row it receives as `receivable`. A trip is the first source in this flow that legitimately raises two opposite-direction obligations, so the old one-row assumption is false.

**Expected.** Trip detail's customer collection row must select only `direction = 'owed_to_us'` and the trip-fare kind; driver fee belongs in the separate driver-payment side.

#### GAP-197 — driver statement days are out of order (P2)

**Reproduction.** Open Sunil's statement for 29 Jul–28 Aug. The live page displayed 24–28 Aug first, then 10–21 Aug, then 23 Aug before 22 Aug. There were no section labels or grouping that could explain the order.

**Root cause.** `api/src/queries/day-record.ts:305` `listDayRecordsForDriver` has no `ORDER BY business_date`; `web/src/features/people/DriverActivitySections.tsx:107` maps `view.days` as received without sorting.

**Expected.** A statement should use one explicit chronological rule, preferably newest-first to match the surrounding history screens, and the API should guarantee it.

#### GAP-198 — utilisation money is truncated (P2)

**Reproduction.** `NC-1234`, 30 May–28 Aug: 91 total days, 1 off-road day, 90 available days, Rs 33,000 earned. UI: `Revenue per available day Rs 366.66`.

**Root cause.** `api/src/domain/reports.ts:693` computes `earnedMinor / BigInt(availableDays)`. BigInt division truncates; it does not use the project's required half-up money rounding.

**Expected.** Rs 366.67.

#### GAP-199 — sticky action still obscures content on tall mobile (P2)

**Reproduction.** At 384×824, open a customer with five payments. Without scrolling:

- `Show all (5)`: y 723–767, 352×44;
- `Collect payment`: y 680–736, 352×56;
- visible intersection: 13 px;
- `elementFromPoint` at the top and centre of `Show all` resolves to `Collect payment`; only the lower sample resolves to `Show all`.

The existing GAP-171 fix adds bottom padding in `Screen.tsx:144–147`, but the sticky element at `:151–161` can still clamp over a child that initially lands beneath it. Scrolling works around the problem. This is a regression/new reproduction against the closed GAP-171 guarantee, not a reopening by assumption.

#### GAP-200 — opening-balance remove target shrinks to 35 px (P3)

**Reproduction.** At 360×640, add an opening-balance entry with the long `QA2 Driver…` label. The icon-only `Remove …` button measures 35×44, below the product's 44×44 commitment.

**Root cause.** `web/src/features/opening-balance/OpeningBalanceScreen.tsx:334–342` places the 44 px icon `Button` in a flex row but does not give it `shrink-0`; the long sibling consumes its width.
