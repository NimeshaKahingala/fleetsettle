# Build tracker

**Not a specification.** `docs/` says what to build and why; this says what is done and in what order. It exists to be ticked off and eventually deleted. Where the two disagree, `docs/` is right.

Fifteen phases. P0–P3 are a strict chain; after that the graph opens up.

**Validated 31 July 2026** against UC §9.1 (product phasing), UI §15 (design build order), IG §12 (bootstrap) and DM §13 (the money-table list). Three corrections came out of that pass and are noted at the bottom.

---

## The five rules that decide the order

**1. `packages/shared` is the root of the dependency graph.** The money codec, the business-date helper and every resource's Zod schema live there and are imported by both sides. Nothing precedes it, and a bug in it is structural rather than local.

**2. The schema is the synchronisation point, and the main lever for parallelism.** Once a resource's Zod schema lands in `packages/shared`, the two tracks separate: the Worker builds against a real Neon branch, the client against mocks derived from *the same schema object*. Hand-mirrored types drift silently and what drifts is a money field (IG §2). So the schema is always a phase's first task, never its last.

**3. Auth blocks the client, not the Worker.** `tests/support/auth.ts` mocks the verifier and mints a user in each W-49 role (IG §8.3), so endpoints are built and fully tested before Asgardeo works. Only the browser needs the real thing.

**4. No cron is ever a prerequisite for a user action.** Confirming a day whose card was never generated creates it. Scheduled work lands *after* the flow it mirrors, never before, and never as the only path to a record.

**5. Reports come after the writes that feed them.** A report with no data behind it cannot be checked against the rule that matters — degrade to "not available", never to zero (W-56).

### Shape of the graph

```
P0 ─► P1 ─► P2 ─► P3 ─┬─► P4 ─┬─► P5 ─┐
 found.    entities   daily    │       ├─► P9 ──► P10 ──► P11 ──► P12 ──► P13 ──► P14
            + all      loop    ├─► P6 ─┤  close   write-  reports offline  cron   messaging
            components         ├─► P7 ─┤          offs
                               └─► P8 ─┘
```

P5, P6, P7 and P8 depend on P4 and on nothing among themselves. Their relative order is a free choice.

### Where the golden fixtures land

They are the regression suite and they gate three phases (FL §9.1). Any change that moves one is a breaking change and must fail loudly.

| Fixture | Figure | Reproduces at the end of |
|---|---|---|
| **G-3** Mileage on an open-ended rental | **7,500** | P5 |
| **G-2** One accident | **15,000** | P8 |
| **G-1** One month of the bus | **134,000** | P9 |

- Found in passing: `stylelint.config.js`'s `tokens.css` override pointed at `web/src/styles/`, not `web/src/design/` (UI §12.2) — fixed. **Ops** — CI creates, seeds and **deletes** a per-PR Neon branch. Not optional on the free plan: branch creation starts failing around nine open PRs, and it fails on someone else's PR for a reason that looks unrelated (IG §9.2). Still blocked on `secrets.NEON_API_KEY` / `vars.NEON_PROJECT_ID`, which don't exist in the repo yet.

Error monitoring — **deliberately deferred**, not wired. Asked: Tail Worker (no new vendor, but still needs a real alert destination — a webhook, Slack, email — that's a separate thing to provide) vs Sentry (needs an account and a DSN) vs defer. Decision: defer — Workers Logs (`observability.enabled`) stays the only observability until there's an actual on-call person and a channel to page; revisit then rather than build an alert that pages no one.

**Depends on** — nothing.

**Done means** — `npm run check` runs both workspaces instead of skipping. `0001` and `0002` are applied to a Neon branch and the DM §13 drift assertion returns zero rows. The codec's tests cover the U+2212 minus, the M-16 cents rule, and a split that sums back to the whole.

# P1 · Identity, tenancy and the access boundary

The one phase where a mistake is a security bug rather than a wrong number.

**Backend** — done.
- `jose` — `jwtVerify` against a **local** JWKS (`createLocalJWKSet`) fetched through KV rather than `createRemoteJWKSet`'s in-memory cache, which only helps the isolate that populated it — refetch-once on a `kid` the cached set doesn't have, then one undifferentiated 401 for every other failure (bad signature, wrong issuer/audience, expired), since none of those distinctions are the caller's to learn from
- `sub → app_user → business_member` **or** `driver.linked_user_id` in one query (`queries/identity.ts`), not three round trips — a linked driver never gets a `business_member` row (DM §3's CHECK constraint), so this is a real second path, not a variation of the first. No membership at all resolves to the same 404 a foreign business would; nothing in the product supports one user across multiple businesses, so this doesn't build a selector for a case that can't happen
- `auth/policy.ts` — one function per row of the W-49 matrix that *is* a flat role check. Two rows aren't: "ownership shares… (own vehicles)" needs P2's ownership records, and "see another driver's data" is `driver_id` scoping in the data layer, not a capability — both noted in the file rather than faked
- The status rule wired once: cross-tenant **404**, lacked capability **403** — proven by `NotFoundError`/`ForbiddenCapabilityError` through the real middleware chain, not asserted in isolation
- The linked-driver test class, exercised against real `vehicle`/`driver` rows via temporary `/api/_probe/*` routes (no CRUD exists before P2) — `GET /api/me` is the one permanent route this phase adds, and doubles as the frontend's role→shell signal
- Rate limiting via the Workers `ratelimit` binding, keyed by `CF-Connecting-IP`, mounted globally — confirmed locally via `wrangler dev` that `namespace_id` needs no separate provisioning step, unlike KV/R2/Queue
- Both Vitest projects (IG §8.1) now have real content: `unit` covers JWKS cache-hit/miss/kid-miss/refetch and the rate-limit middleware with a mocked `fetch`/fake KV, no Postgres; `integration` covers the full matrix above through `app.request()` against the real Neon branch, using a real ES256 keypair (`tests/support/jwks.ts`) to sign test tokens — `auth/verify.ts` is not mocked, only the IdP is

**Frontend** — the router, the first-run gate and role→shell selection are done; real Asgardeo wiring is deliberately deferred and no longer blocks any of it (see below).
- `@tanstack/react-router`, code-based routes (no `router-plugin` codegen — this repo hand-writes migrations for the same reason: a generated `routeTree.gen.ts` is a file nobody reviews). `web/src/app/router.tsx` builds the tree from a factory (`createAppRouteTree(today, history?)`) so tests inject `createMemoryHistory` while `main.tsx` gets the real browser history — one router *type* registered via `Register`, many instances
- `FirstRunGate` (`GET /api/me`, `retry: false` — the default `QueryClient`'s 3-retry backoff otherwise left the first screen on "Loading…" for several seconds before an unrecoverable error ever surfaced) — a 404 renders `CreateBusinessForm` (F-0.1's documented no-membership-yet case); success routes by role per UI §1.1. Only the Operate shell has real screens this pass; Review/Mine render a placeholder (`NotBuiltYetScreen`) until Web-P9/P10
- `Screen` gained an optional `onBack` (44×44 `ChevronLeft`, §7.5/§7.2's wireframes) — the first primitive extension since P2, needed the moment a route could be left rather than just switched
- **`web/src/lib/auth-stub.ts`** — a stand-in token getter, opt-in via `VITE_AUTH_MODE=stub` (never `import.meta.env.DEV`, since Playwright's e2e project runs a real production build, where `DEV` is always false). Resolves an obviously-fake, unsigned token that a real Worker's JWKS check will always reject with a real 401 — it cannot make the API accept anything, it only gets a request *issued*, which is what makes it mockable at all. Checked against two real builds rather than assumed: with the flag unset the branch is unreachable (`import.meta.env` compiles to `{}`, so the comparison is constant-false), but Rollup does not tree-shake the unreachable branch's string literal out of the bundle — inert, but "unreachable" and "absent" are different claims, recorded in the file's own comment so a bundle grep doesn't get mistaken for a real leaked credential. Wired into `npm run dev` and into Playwright's **build** step (env vars are inlined at build time, so setting it only on `preview` would miss the already-built bundle)
- This unblocked `e2e/smoke.spec.ts` to mock `/api/me` and vehicle/people reads via `page.route()` and exercise real screens end-to-end in Chromium: the first-run 404 case, a deep link straight to a vehicle's detail with no list visit first, the browser back button returning from detail to list, and a tab change updating the URL so a reload keeps the manager where they were — 4/4 passing
- API client's token getter was already injected (P2); a 401-retry-once backstop is **not built** — not yet needed since nothing issues a real request against a real 401 without Asgardeo, and it belongs with Web-P12, not this pass

**Depends on** — P0. Real Asgardeo wiring is its own phase now (**Web-P12**, deliberately sequenced last — see the frontend roadmap plan), not a prerequisite for any screen work between here and there; `@asgardeo/auth-react`, PKCE, refresh, and swapping `auth-stub.ts`'s stub for the real token getter all wait on the same console changes (token type JWT, binding None, redirect URLs) as before.

**Done means** — a probe endpoint passes the whole matrix: happy path · 401 missing header · 401 verifier throws · 403 capability · **404 for another business**. A linked-driver token gets 404 for another driver's row. `getAccessToken()` is on the wire, never the ID token (IG §7.3).

  Found and fixed three recurring bug classes here, each fixed at the structural level rather than per-form, since every P3+ form inherits the same shape:
  1. **The wire/domain mismatch for any zod schema with `.transform()`** (money's `moneyWireSchema`, dates' `businessDateSchema`) — its `z.infer` (output) type differs from its `z.input` (wire) type, but `MoneyField`/`DateField` produce/consume the *domain* type (`Minor` bigint, `BusinessDate` string) directly. Fixed once with `lib/optionalTextField.ts`'s `blankToUndefined = { setValueAs: (v) => (v === "" ? undefined : v) }`, spread into `register(name, blankToUndefined)`.
  3. **A cross-field validation error hidden inside a collapsed `Disclosure`** — W-55 (a person needs an NIC or a mobile) attaches its error to a field at level 2, invisible on a failed submit if that section is still collapsed. Fixed by adding `Disclosure`'s `forceOpen?: boolean` prop, driven by `errors.fieldName !== undefined`.

# P3 · The daily loop

**The first vertical slice, and the flow the product is optimised for.** F-4.2, F-4.3, F-4.6.

**Shared** — `day_record`, `obligation`, `payment`, `allocation` schemas.

**Backend**
- `domain/confirmDay.ts` — four inserts in **one transaction** — done. One endpoint, `POST /api/day-record/confirm`, serves all three of F-4.2's buttons and F-4.4 via a `action: "paid_in_full" | "something_else" | "did_not_run"` discriminated union — `paid_in_full`'s earned/received are resolved server-side from `findDailyLeaseRateForDate` (the rate in force *on that date*, not just today's, since a catch-up day's rate can differ — F-4.3's effective-dating), never sent by the client. `obligation.settled_minor`/`status` are computed once, correctly, from the given earned/received at insert time — never a follow-up `UPDATE`, which is what keeps this "four inserts" rather than "four inserts plus one". A `did_not_run` day writes only `day_record` (INV-6: no obligation for a day nothing was owed on)
- Idempotency on `(daily_lease_id, business_date)`; a second confirm is a no-op — done. `domain/confirmDay.ts` checks for an existing row *inside* the transaction (any state at all counts as settled — there's no `generate-day-cards` yet to ever leave one at the pre-generated-card `open` state, so that branch is dead code today and documented as such rather than half-built against a state that can't occur) and returns it unchanged; a concurrent double-tap is additionally caught as a unique-violation-is-success at the `day_record_daily_lease_id_business_date_key` constraint (CLAUDE.md's cron idempotency rule, extended to this user-triggered action, the same way `opening-balance`'s commit endpoint already does)
- Day-card creation on demand when the card does not exist — done, by construction: confirming inserts `day_record` directly in its final confirmed state (never an intermediate `open` row), so there is nothing separate to "generate" first
- `PERIOD_CLOSED` mapped from the trigger violation — **no application pre-check** — done. New `isPeriodClosedViolation()` (`db/pg-error.ts`) disambiguates `assert_period_open()`'s `RAISE EXCEPTION` from the schema's other bare-SQLSTATE triggers (`assert_shares_total`/`assert_advances_settled`/`assert_split_sums`, all still `P0001`) by message text, the same role a constraint name plays for `isUniqueViolation`/`isExclusionViolation`. New `queries/accounting-period.ts`'s `resolvePeriodLinkage()` is the first real use of W-35's `posted_period_id`/`belongs_to_period_id` split outside opening balances — `posted_period_id` is always the currently-open period, `belongs_to_period_id` is set only when the business date falls in a *different*, earlier period (there is only ever one period per business until P9 can close one, so this is correct now and already shaped for when that stops being true)
- `earned` and `received` stored separately, never collapsed — done (INV-2). `day_record.earned_minor` is a real column; `receivedMinor` on the wire is assembled from the day's `obligation.settled_minor` (DM §1.3) — a new `GET /api/day-record/{dailyLeaseId}/{businessDate}` (F-4.1, added alongside since the frontend needs it to know a day is already confirmed on load) does this same join to answer "what happened today," returning 404 for "not yet confirmed" rather than a fabricated zero row (day_record rows are never deleted, so 404 here only ever means "no such row yet")

# P5 · Rent, billing periods and mileage

F-2.x. **Gates G-3.**

**Shared** — `lease-billing` schemas (`billingPeriodResponseSchema`, `recordOdometerReadingRequestSchema`, `mileageAssessmentResponseSchema` + its splits, `renewLeaseRequestSchema`, `recordPaymentRequestSchema`); `startLeaseRequestSchema` (arrangement.ts) gained the handover-odometer fields. A new `splitInteger` (packages/shared/src/split.ts) is the largest-remainder primitive on plain integers — `money.ts`'s `split` now wraps it rather than duplicating the algorithm, so kilometre splitting (below) and money splitting share one tested implementation. `dates.ts` gained `addCalendarMonths` — day-of-month-preserving, clamped to the target month's length — which is the one line making §7.3's 31/28/31/30 reproducible arithmetic instead of drift accumulated period-over-period.

**Backend**
- Billing-period generation, idempotent on `(lease_id, seq)` — done. `domain/billing-period.ts`'s `generateNextBillingPeriodTx` computes period *N*'s boundaries from the lease's own anchor date (`addCalendarMonths(startDate, N-1)` through the day before `addCalendarMonths(startDate, N)`), never chained off the previous period's end, and raises that period's rent `obligation` in the same transaction — "a billing period on its own owes nobody anything" (F-2.1). The public `generateNextBillingPeriod` wraps it in its own transaction and catches a `billing_period_lease_id_seq_key` collision as the idempotent-replay path (concurrent double-submission, not sequential re-calls — calling it twice in sequence legitimately advances the schedule by two periods, since this function has no notion of "today"; deciding *when* to call it is P13's cron's job once it exists). `POST /api/lease/{id}/billing-period` (generate) + `GET .../billing-period` (list) stand in for that cron until it exists
- `POST /api/lease` now writes the lease, its handover `odometer_reading` (INV-19, required by schema whenever a mileage limit is set) and the **first** billing period in one transaction (`domain/lease.ts`'s `startLease`, composing `generateNextBillingPeriodTx` inside the same transaction rather than opening a second one) — the first rent due is no longer left for a cron that doesn't exist yet (CLAUDE.md → Writes: "no cron is a prerequisite for a user action"). This is a real behaviour change from P2: starting a lease now requires an open accounting period, the same as every other money write
- Rent as a **fixed amount per period**; mileage allowance as **per day × days in the period** — the one place consistency would be a bug (W-25) — done, `allowance_km = daily_limit_km × days_count`, `days_count` read back from the generated column, never computed twice
- Excess assessment, one-directional: under the allowance produces no refund, credit or carry-forward — done. `domain/mileage.ts`'s `assessMileage`: which billing period(s) a reading closes out is derived from the date range since the *previous* reading (`findBillingPeriodsInRange`), never chosen by the caller. One period → a plain assessment; more than one (a missing boundary reading, §7.3's March case) → combined against their summed allowance, excess split by days via `splitInteger` (largest-remainder, INV-26), marked `isEstimated`. An excess at or below `businessSettings.autoWaiveThresholdMinor` auto-waives on the spot — obligation `waived_minor` set, plus an `auto_waiver` adjustment row (F-2.4) — reusing P4's `computeObligationStatus` and `adjustmentType` machinery rather than a second implementation. Idempotent on `(lease_id, read_on)` — migration `0005_odometer_reading_lease_date_unique.sql` adds the partial unique index (partial because `odometer_reading` also serves trip/oversight readings with no `lease_id`, W-12); the up-front existence check matters as much as the catch, since by the time of a genuine replay the just-recorded reading is itself the *latest* one for the lease, and computing "driven since the previous reading" from it would silently produce a nonsensical zero-period assessment instead of replaying the original result — the same lesson P3's `confirmDay` idempotency already encodes, applied here a second time. `POST /api/mileage-assessment`
- A billing period is **not** an accounting period; they coincide only by accident (W-40) — done, no code path derives one from the other
- F-2.5 renew — done. `PATCH /api/lease/{id}/renew`: old periods keep their old figure (already frozen onto `billing_period` at generation time); this only changes what the *next* generated period picks up — a plain field update, no effective-dated history table needed
- F-2.2 collect payment, generalised — done, ahead of schedule because `AllocationPreview` (P2) had no backend behind it yet. `POST /api/payment`: oldest-`due_on`-first allocation (§6.5) against a party's outstanding `owed_to_us` obligations, reusing the exact allocation shape P4's offset already proved (`findOutstandingObligationsForParty` generalises `findOutstandingObligationsForDriver` by party type). A surplus beyond every outstanding due comes back as `unallocatedMinor` rather than silently dropped — F-2.2's "overpayment held as customer credit" — though actually applying it forward against a future due isn't wired yet (recorded rather than faked, same convention as P4's partner current-account gap)

**Found and fixed along the way**: the existing P2 lease-creation test assumed no accounting period was needed to start a lease — true before this phase, false after (money now moves at creation). Updated rather than left red.

TRACKER.md's own P13 entry records how this was found: `GET /api/home/deposit-releases` reads deposits in `hold_window`, and nothing in this codebase had ever put one there, because closing a lease — a whole Phase-1 flow (W-26) — had never been built. **Shared** — `lease-closure.ts` (new): `closeLeaseRequestSchema`/`closeLeaseResponseSchema`, `leaseClosureSummaryResponseSchema`, `settleLeaseDepositRequestSchema`/`settleLeaseDepositResponseSchema`. `arrangement.ts`'s `startLeaseRequestSchema` gained an optional `depositAmountMinor` (F-2.1's own handover deposit, the row this flow later settles); `leaseResponseSchema` gained a sibling `startLeaseResponseSchema` carrying the new `depositId` rather than forcing every lease-reading endpoint to compute one.

**Backend** — four endpoints against the lease's own `active → closing → closed` state machine, matching UC-16's explicit running order (W-26: "do not let steps be skipped forward"):
- **`POST /api/lease/{id}/close`** (steps 1–3, `domain/lease-closure.ts`'s `closeLease`) — "stop the clock" is `status → 'closing'` plus its `end_date`; `generateNextBillingPeriodTx`'s own `status !== 'active'` guard is the *entire* mechanism that stops further dues, never a second check. "Decide the final period" adjusts the covering billing period's own *obligation* via `applyAdjustmentTx` (F-2.4's existing mechanism, reused rather than reimplemented) — `full` leaves it untouched, `days_used` prorates via `split()` (the same largest-remainder primitive P5's mileage splits use) and records the difference as a `goodwill` adjustment (UC-16's own table names this case "goodwill"), `agreed` records an `agreed_discount` or `extra_charge` depending on which side of the original figure the agreed amount lands. The covering period's own `period_end`/`allowance_km` are shortened to the days actually covered whenever closure lands early — **regardless of `finalPeriodMode`** — so mileage is never measured against days that were never used; `rent_amount_minor` itself is never touched (W-25: fixed, regardless of days). "Final mileage" is a closing odometer reading run through the *existing*, unmodified `assessMileage` (F-2.3) as a second, separately-transactional call — already idempotent and atomic on its own, so composing it into the first transaction would only duplicate that function's own tx-core for no correctness gain.
- **`GET /api/lease/{id}/closure-summary`** (step 4/INV-18, `getLeaseClosureSummary`) — realized that "unpaid dues from earlier periods," "this period's amount" and "excess mileage" are the same shape of fact (an unsettled `owed_to_us` obligation against this customer), so it is one oldest-due-first list (`findOutstandingObligationsForParty`, extended with `kind`/`dueOn` for display) plus any open incident tied to this lease (`listOpenIncidentsForLease`, new — scoped by `incident.lease_id` directly rather than the whole vehicle's history). INV-18 itself ("does not block, refuses to let you do it blind") is this endpoint simply existing to be called before settlement, not a stored flag.
- **`POST /api/lease/{id}/settle-deposit`** (step 6/W-29/W-44, `settleLeaseDeposit`) — refund in full, retain a portion with a reason, or hold for `business_settings.deposit_hold_days` (new `hold_window` status transition, no migration needed — `hold_release_date` already existed on `deposit`, unused until now). Requires the lease past step 1 (`status !== 'active'`). **"Apply against what is owed" (F-8.4) is deliberately not built** — it needs the same oldest-first obligation-settling wiring `recordPayment`'s `allocateAgainstOldest` already solved for real cash, and reusing that verbatim would wrongly create a new `payment` row for money that was already held; a parallel apply-without-a-payment-row path is real, separate design work, recorded rather than half-built.
- **`POST /api/lease/{id}/close-out`** (step 7, `closeOutLease`) — `status → 'closed'`, and this lease's own future `vehicle_day_allocation` rows beyond the closing date are freed (`deleteLeaseAllocationAfter`, mirroring F-5.5's `deleteAllocationDaysForTrip`) — "car marked available" made literal, since P13's cron would otherwise keep this vehicle looking occupied by a lease that no longer exists. Days up to and including the closing date are left alone; they happened.
- **Deposit intake generalised, not rebuilt**: `queries/driver-money.ts`'s `NewDeposit`/`DepositRow` were driver-only (`insertDeposit` hardcoded `partyType: 'driver'`); now they carry `partyType`/`partyCustomerId`/`leaseId` too, and a new `takeCustomerDepositTx`/`takeCustomerDeposit` (`domain/deposit.ts`, split into a `tx`-core and a `writer`-wrapper the same way `generateNextBillingPeriodTx`/`generateNextBillingPeriod` already are) lets `startLease` take a deposit inside its own single transaction. `takeDriverDeposit` (P4/F-6.7) is untouched behaviourally — only its one call site now states `partyType: "driver"` explicitly instead of relying on a hardcoded default.

Deliberately does not merge in `day_record`'s state (lost/ran) — occupancy and outcome are different questions. `GET /api/vehicle/{id}/calendar?from=&to=`
- **INV-1** (vehicle double-booking returns 409) — already done in P2, unchanged here: booking a trip writes its full-range `vehicle_day_allocation` at booking (DM §4.1), so the invariant existed as soon as the booking endpoint did

# P13 · Scheduled work

Two of TS §4's five Cron Triggers built this pass: `generate-day-cards` and `generate-billing-periods`. `dispatch-messages` has nothing to dispatch into until P14; `paperwork-warnings`/`deposit-hold-release` turned out, on reading F-2.7/UC-92 closely, to be a **read** the home screen calls live (UC-92: "warns... on the home screen"; F-2.7: "on the release date, the deposit appears on the home screen") rather than a job that writes anything — no cron needed for either, and both are now built as `GET` endpoints (below), closing out this phase's own remaining scope in a same-phase follow-up.

**Backend**
- **`generate-day-cards`, plus the arrangement-A calendar extension DM §4.1 assigns to the same cron** (`domain/day-card-generation.ts`) — done. This closes the two things P2 deliberately left undone: `vehicle_day_allocation` now actually materialises on a rolling 90-day horizon for a **lease** (through `end_date`, or the horizon if open-ended) and for a **daily lease** (its own pattern days, paired with a `day_record`) — P2's lease/daily-lease endpoints only ever wrote the arrangement's own row, so **INV-1 was unenforced for both until this job existed.** Arrangement B gets its allocation row across the **full** horizon regardless of period state (so a lease booked far out still collides correctly, DM §4.1's own example), but its paired `day_record` only for the portion inside the business's own **currently open** accounting period — `day_record.posted_period_id` is `NOT NULL`, and periods open one at a time by an explicit close (P9), so a date 60 days out may have nowhere to post yet; it gets its allocation now and its day_record on a later run, once that period exists. An existing allocation (a trip's, most often) is always left alone — checked before generating, never overwritten
- **`isPatternDay`'s "alternate" reference point is a recorded judgment call**, not a documented rule: F-1.7 says "alternate days" with no reference point stated anywhere, so this treats the lease's own `effective_from` as day zero (always "on"). F-1.7's "individual days skippable" clause has no column to hold an exception (`daily_lease` carries no per-day override) and is not implemented
- **`generate-billing-periods`** (`domain/billing-period.ts`'s `rollDueBillingPeriods`) — done. One function, two callers: the exact `generateNextBillingPeriod` a manual `POST .../billing-period` call (P5) already uses, never a second implementation of the period-boundary arithmetic. A lease more than one period behind catches up in a bounded loop (24 periods, two years) rather than waiting for 24 more days of cron runs
- **Both jobs are unscoped by `business_id`, deliberately** (`queries/scheduled.ts`'s own doc comment) — CLAUDE.md's tenancy rule exists to stop a *request* from crossing tenants; a Cron Trigger is not a request, and it must see every business to do its job. Each unit of work (one lease, one daily lease) is wrapped in its own try/catch and collected rather than thrown, so one bad row never takes the whole run down — the same isolation `sumDepositsHeld`'s bounded read loop already established one layer down
- **Idempotency by insert, not by pre-check-then-hope**: both jobs' bulk writes use `.onConflictDoNothing()` (`insertAllocationDaysIdempotent`/`insertDayRecordsIdempotent`) — deliberately a **different** insert path from `insertAllocationDays` (queries/trip.ts), which a real trip booking must keep using, since a genuine INV-1 conflict there is a 409 the caller needs to see, never silently dropped. Only the cron's own idempotent re-run gets to treat a conflict as "someone already did this"
- **Wired as a real Cron Trigger** — `wrangler.jsonc`'s `triggers.crons` (`"30 20 * * *"`, 02:00 Asia/Colombo), `src/scheduled.ts`'s `scheduled()` handler, added onto the same Hono `app` instance (`Object.assign(app, { scheduled })`) rather than replacing the default export with a plain `{fetch, scheduled}` wrapper — the latter would have lost `app.request()`, the exact method every integration test calls against this same default export
- **A single business timezone for every business, not resolved per-business** — `scheduled.ts` calls `businessToday()` once (`Asia/Colombo`), matching every business currently in this system. A real per-business-timezone cron would resolve each business's own `business.timezone` before deciding "today" for its leases; not built, recorded rather than guessed at
- **`GET /api/home/paperwork-warnings`** (F-10.1/UC-92, `domain/home.ts`'s `getPaperworkWarnings`) — every `vehicle_document` and `driver.licence_expiry` due inside the business's own `paperwork_warn_days` window (default 30, `business_settings`), already-expired ones included and flagged `isExpired` rather than dropped — the Accept clause is "warns... and keeps warning until the new date is entered," so there is no separate "already expired" list to fall off of. Reads the server's own `businessToday()`, never a query-param date, since this endpoint has no caller-supplied "as of" concept the way a report does
- **`GET /api/home/deposit-releases`** (F-2.7/UC-16 step 6/W-29, `getDepositReleases`) — every `deposit` in `hold_window` whose `hold_release_date` has arrived, with its held balance (`sumDepositMovements`, queries/driver-money.ts — the same bounded per-row loop `sumDepositsHeld` already justifies) and the party's name. # Web-P5 (calendar) · F-1.5's vehicle calendar

UI §7.6: "the one screen that justifies a custom date component" — a month grid, 7×~44px cells, colour plus glyph per day so it survives colour blindness and greyscale printing, a fixed legend below rather than a tooltip. - UI §7.6 asks for an "orange wash" on arrangement C (on a trip / hold). Reused it rather than inventing a raw hex or a new token unilaterally; the reuse is a color match, not a semantic one (a trip isn't "serious"), and is recorded here as a gap worth a real token addition later, not a decision to be silently repeated.
- **`isHold` has never been set to `true` anywhere in this codebase** — `bookTripRequestSchema`'s own doc comment already records that booking a trip writes `booked` outright, never modelling the `hold` state ST-5 describes. **New test factory:** `TestContext.createMileageAssessment` (bare row, mirroring `createBillingPeriod`'s own "figures under the test's control" convention) and `trackCreatedMileagePackage`, since `mileage_package` had no teardown helper at all before this.

**Depends on** — nothing new; both gaps were pure absence, no migration needed (`mileage_package`'s DDL was already live).

**Done means** — 46/46 passing in `api` (4 new in `mileage-package.test.ts`; 4 new in `lease.test.ts`'s dues describe block, including the three-source-path reassembly proven directly); `npm run check` clean across all three workspaces. **Found and fixed, one line away from mattering:** `CreateDriverForm`'s own schema and `mutationFn` have declared and submitted `driverTripFeeMinor` since P2, but the form never rendered a `MoneyField` for it — a driver's trip fee could never actually be set through the UI that exists to set it. # Web-P8a · Incidents (F-3.4/UC-12), §6.6's container, W-9/W-10/W-11

The backend has carried the whole incident lifecycle since P8 — open, off-road, customer contribution, insurance claim, close, the bottom line — with none of it reachable from a screen. Three small backend gaps surfaced while building the container, all the same shape as Web-P7's: data the domain already computed or stored, never projected onto the wire.

**Gap 1 — the detail response never carried what it would take to act on a reload.** `computeIncidentBottomLine` already fetches every recovery row to sum them, and `insurance_claim` was written alongside a submitted claim, but neither the recovery rows themselves nor the claim ever reached `GET /api/incident/{id}`'s own response — a manager returning weeks later to mark a contribution received, or settle a claim, would have had no id to act on unless the original POST response was still in memory. Fixed: `incidentDetailResponseSchema` gained `recoveries`/`insuranceClaim` fields; `findInsuranceClaimForIncident` (new query, mirrors `findIncidentRecoveryBySource`'s "look up by incidentId, trust the caller already validated business" shape) and the already-existing `listIncidentRecoveries` are now both composed into `incidentDetailToResponse` (`handlers/incident.ts`), reached by all three of `openIncidentHandler`/`getIncidentHandler`/`closeIncidentHandler` at once, since they all share the one composition function.

**Gap 2 — no read at all for "what has this vehicle had."** Vehicle overview's own Incidents section (below) needed a list; `listIncidentsForVehicle` (new query) is deliberately **not** filtered to open-only, unlike `listOpenIncidentsForLease` (F-2.6's closure-summary read) — the section answers "what happened to this vehicle," not just "what still needs a decision." New route `GET /api/vehicle/{id}/incident`, gated `dailyOperations` (matching every other incident endpoint's own gate) rather than this file's usual `manageEntities`, a deliberate, recorded divergence.

**Gap 3 — the incident screen's own "Repairs" step had a total but no itemised list.** `sumIncidentCostMinor` (existing) answers the bottom line's own excludes-voided total; nothing let the screen show *which* invoices make it up. New `listExpensesForIncident` query and `GET /api/incident/{id}/expense` route mirror Web-P7's own `listExpensesForTrip`/`GET /api/trip/{id}/expense` exactly — voided rows included and struck through (W-50), not excluded the way the bottom-line sum is.

**Not fixed, recorded instead:** W-11's "hidden unless enabled — major damage only" has no backing settings field anywhere in the schema, and never has — `InsuranceClaimSheet`'s own action is always offered rather than inventing a toggle this pass doesn't own.

**`IncidentScreen`** (`/incidents/:id`) — §6.6's container, opened once and revisited over weeks, not a wizard: every action (off-road, a new contribution, a claim) stays available regardless of `status`, since `closeIncident` itself never guards on it either — closing is a manual bookkeeping wrap-up, not a lock. The bottom line (total repairs / recovered / pending recovery / net cost to you) renders "at the top, always" per UI §7.10, real zeroes rather than `NotAvailable` (this figure is never a gap — `sumIncidentCostMinor`'s own doc comment already establishes zero as a real total here). Off-road, once recorded, shows as read-only info; **re-recording it is not offered** — `updateIncidentOffRoad` has no guard against being called twice and `recordOffRoad`'s `credit_days`/`extend` paths would insert a second adjustment or push the lease end date out again, so the client-side rule (hide the action once `offRoadFrom` is set) is what keeps that footgun out of reach, not a change to the domain. A customer recovery row is tappable while `received < agreed`; the insurance claim, if one exists, gets its own card, tappable while `submitted`/`in_progress`. Close is the screen's one primary action, offered until `status === "closed"` — no `Dialog` (closing an incident is not one of the three reserved cases: INV-1, INV-17, M-10).

**`ReportIncidentSheet`** (F-3.4 step 1) — level 1 is just the date, defaulted to today (U-2); description is level 2. Photos are not built — no R2 presigned upload, the same decision the plan already made for this pass, matching `CloseLeaseScreen`'s own condition-step gap. Opened from `VehicleOverviewScreen`'s new "Vehicle actions" menu (below); on success, lands directly on the new incident's own screen.

**`OffRoadSheet`/`CustomerContributionSheet`/`InsuranceClaimSheet`/`SettleInsuranceClaimSheet`/`RecoveryReceivedSheet`** — five small, single-purpose sheets, one per backend endpoint, following `AdjustObligationSheet`'s money-plus-note shape and `CloseTripSheet`'s sync-on-open convention. `RecoveryReceivedSheet` pre-fills at the current `receivedAmountMinor` (or the full agreed amount, if nothing has arrived) since the endpoint takes a total-so-far, not an increment — the same one-field arithmetic-avoidance `AdjustObligationSheet` already established for a different field.

**Found and fixed while writing this sheet's own test:** `RecoveryReceivedSheet`'s first draft posted `receivedAmountMinor` as the raw `Minor` (`bigint`) rather than `toWire(amountMinor)` — `JSON.stringify` cannot serialize a `bigint` at all, so this would have thrown on the very first real call, never a wrong-number bug, a hard failure. Caught before any test ran against it, by re-reading the diff against every other sheet's own `toWire` call.

**`VehicleOverviewScreen` reshaped: one action becomes a menu.** The app-bar's single slot (§4.2) held only "View calendar"; it now opens a "Vehicle actions" `ActionSheet` ("View calendar", "Report incident"), the same pattern `LeaseHubScreen`'s "Lease actions" and `PeopleListScreen`'s "Add" already established for exactly this reason. **Depends on** — `POST/GET /api/incident*` (all P8), `GET /api/vehicle/{id}/incident`/`GET /api/incident/{id}/expense` (new, this phase); `MoneyField`/`DateField`/`NoteField`/`ActionSheet`/`NotAvailable` (all pre-P8a).
