### The five rules that decided the order

Still binding on everything in [Plan.md](Plan.md):

1. **`packages/shared` is the root of the dependency graph.** A bug in it is structural, not local.
2. **The schema is the synchronisation point, and the main lever for parallelism.** Once a resource's Zod schema lands in `packages/shared`, the two tracks separate: the Worker builds against a real Neon branch, the client against mocks derived from *the same schema object*. Hand-mirrored types drift and what drifts is a money field. **This rule is what makes the plan's Track A / Track B split legal.**
3. **Auth blocks the client, not the Worker.** `tests/support/auth.ts` mints a user per W-49 role, so endpoints are tested before Asgardeo works.
4. **No cron is ever a prerequisite for a user action.**
5. **Reports come after the writes that feed them.**

## 5. The traps

Things that cost a session each when rediscovered.

**Testing and environment**

- **`npm run check` does not run the api integration suite.** `api`'s `test` is `vitest run --project unit`; `test:integration` is separate and needs a live Neon branch. A green `check` says nothing about endpoint behaviour.
- **`mintUser(db, ctx, businessId, role)` takes the role as an explicit argument everywhere it is called — which means no test in this codebase has ever exercised the role a real signup actually gets.** GAP-42's bug (`createBusiness` granting `owner`, the one role with no screen) sat behind 386 green integration tests for exactly this reason: every one of them minted its `owner`/`manager`/`driver` directly rather than going through `POST /api/business` and reading back what it assigned. `business.test.ts`'s own happy-path test does call the real endpoint — and had asserted the wrong role as correct, so even the one test positioned to catch this had been pinned to the bug (the same shape as A9a's `voidExpense` regression test). Worth a standing question on any new setup/provisioning path: is there a test that reads back what the system decided, or only tests that assume a value and mint it directly?
- **The Neon branch has a connection ceiling.** Every integration file opens its own `Pool` and holds it to `afterAll`, so file-level parallelism opens all of them at once — `vitest.config.ts` sets `fileParallelism: false` for exactly this. On one long-lived interactive branch it still surfaces as `Connection terminated unexpectedly` at a **different, random** test each run. **A failure that moves between runs, in files the change never touched, is the environment.** Re-run the touched file alone before believing a regression. Web-P6d, Web-P7, Web-P8a and Web-P8b each hit it; P8a's session saw 15 failures across 7 untouched files, P8b's saw 2 in `auth.test.ts` that passed 9/9 alone.
- **A dedicated Neon branch plus `TEST_PARALLEL=1` cuts a full local `test:integration` run from ~29 minutes to ~105 seconds** — a ~16x speedup, measured both ways on the *same* branch (`test-parallel`, `br-lingering-violet-afr5li7f`, forked from `main`) so nothing else differs. `api/.dev.vars`'s `TEST_DATABASE_URL` now points at it; the old shared `test` branch is unused, not deleted. The env var sets `fileParallelism: true` with `poolOptions.threads.maxThreads: 4` (`vitest.config.ts`) — bounded well under the ~14-file ceiling above, so it doesn't reintroduce that failure mode. Opt-in and off by default; CI and anyone who hasn't set up a personal branch are unaffected.
- **The connection flakiness above can also surface as a foreign-key violation mid-cleanup, not just a raw timeout.** Found running `TEST_PARALLEL=1` twice in a row: run one failed 6 tests in `mileage-assessment.test.ts` (`billing_period_lease_id_fkey`), run two failed 2 in `day-record.test.ts` (`day_record_daily_lease_id_fkey`) — different file, different constraint, different count, both files 25/25 re-run alone. Same "moves between runs" signature as above, not a cleanup-ordering bug — checked `trackCreatedLease`'s teardown before concluding that, and it's correctly written (re-queries and deletes child rows before the parent, one sequential closure, no bug found). A dropped connection mid-closure can still leave a delete half-done; the fix is the one already established above, not a change to test support.
- **`audit_log` no-ops every `DELETE`** (`DO INSTEAD NOTHING`, migration `0001`). An `app_user` is permanent from the moment anyone acts. Test cleanup must not try — it will compile, run, and silently do nothing. The fix lives in `tests/support/auth.ts`/`factories.ts`; production only ever revokes `business_member`.
- **17 ESLint warnings are expected**, all `react-refresh/only-export-components` in `router.tsx` (15, one per route component — 14 until B10 added `StartDailyLeaseRoute`), `ApiContext.tsx` (1) and `AuthActionsContext.tsx` (1, added in B0 — the same context-with-a-hook shape as `ApiContext.tsx`). A direct consequence of the code-based-router decision plus that shared pattern. **The count rises by one with every new route and that is correct**; 0 *errors* is the bar. Do not "fix" these by splitting the route tree or the contexts.
- **`eslint-plugin-jsx-a11y` is deliberately absent** — its published peer range caps at ESLint 8/9 and this repo is on ESLint 10. **axe-core in Playwright is the a11y gate** until it catches up.
- **Two test files sharing a base name with only the extension differing breaks typescript-eslint's `projectService`, reproducibly, with a "not found by the project service" parsing error — not an environment or caching artefact.** Found building B4: five screens each grew a `Screen.test.ts` (pure view-model functions) alongside the existing `Screen.test.tsx` (render tests), and every `.test.tsx` half of a same-stem pair started throwing, across separate process invocations, with `cwd` and the file's own existence both independently confirmed correct first (a red herring this session chased for several tool calls before testing the actual variable — file-stem collision — rather than the environment). `web/tsconfig.json`'s `include` glob covers both files individually; the crash is specific to the pair coexisting. **Fix: merge into the one file this codebase's own convention already uses** (one test file per screen, `StartLeaseScreen.test.tsx`'s own shape — pure-function `describe` blocks and render `test`s in the same file) — not a `tsconfig`/`allowDefaultProject` workaround, since the simpler fix is also the one that matches how every other screen here is already tested.
- **Neon's Free plan rejects an explicit `suspend_timeout` on branch creation outright** — a `412` with no error body surfaced by `create-branch-action`, even though the value passed (300s) matched the plan's own fixed default exactly. Confirmed against Neon's own plans doc: *"Can I disable scale-to-zero? Free: No, it's always enabled (5 min idle timeout)"* — the setting isn't configurable via the API on this plan at any value, matching or not. Cost three failed CI runs before the parameter itself was suspected (the first three failures were a separate, missing-secrets cause). Fixed by omitting it from `integration.yml` entirely; Free already suspends at 5 minutes regardless, so nothing is lost.
- **The free plan caps a project at 10 branches and starts failing branch creation around nine open PRs**, on *someone else's* PR, for a reason that looks unrelated (IG §9.2) — why `integration.yml` is one workflow, not two. Delete a hand-created scratch branch (a `migrate-check-*` from testing a migration manually) once its job is done rather than leaving it as permanent headroom loss.
- **`2822193` shipped with `npm run typecheck` broken** — `api/vitest.config.ts`'s `process.env.TEST_PARALLEL` trips `noPropertyAccessFromIndexSignature` (`tsconfig.base.json`), TS4111, since the index-signature access needs bracket notation (`process.env["TEST_PARALLEL"]`). `TEST_PARALLEL=1` had been run and verified, but plain `npm run check` apparently hadn't, on this one file. One-line fix; found and fixed at the start of A2 before `check` could pass at all.
- **Nothing pushed straight to a feature branch (`build/p0-foundation` included) has ever run through CI.** `checks.yml` and `integration.yml` both trigger only on `pull_request` into `develop`/`main`; a bare `git push` to any other branch triggers neither. Every gate result recorded in this document through B0 was a local run substituting for that, not a CI-confirmed one. **Changed 5 August 2026 (A9a):** stop running the full local integration suite at all — run only the touched file locally, push, and open a PR into `develop` so `integration.yml`'s fresh-ephemeral-branch-per-PR run carries the full-suite cost instead, in parallel with the next item. It is also strictly better at the one thing the shared branch keeps failing at: A9a's own verification, run against a throwaway branch created via the Neon MCP tools rather than `api/.dev.vars`'s long-lived one, came back **378/378 in one pass with zero connection flakiness** — the failure mode above is specifically a contention problem, and a branch nobody else is using has none.
- **The `api` integration count recorded in §1's gate table had drifted to a stale `388`** before A9a touched anything — corrected to the verified **378** (ground-truthed two ways: the full CI-equivalent run above, and a plain `grep -c` across every `tests/integration/*.ts` file). Worth a reminder that a number in this document is only as good as the run that last produced it; re-verify rather than carry one forward on trust when a full run is available anyway.
- **Mocked/stub-mode review cannot see `AuthGate` or `FirstRunGate`'s non-`AppShell` states, because the mock replaces the exact code path in question.** `VITE_AUTH_MODE=stub` — used by every test file and by `UI-UX-REVIEW.md`'s own Playwright pass — skips straight past sign-in. GAP-49 (6 Aug, live testing) lived on precisely that boundary and had already cost one near-miss: B8's own writeup flagged "one real browser round trip still unexercised" as an open risk and left it open. **Standing rule: anything touching `AuthGate`, `FirstRunGate`'s non-`renderOperate` branches, or any component that can render outside `AppShell`, needs one real-browser check, both colour schemes, before being called done.** Not a preference — mocked review is structurally incapable of catching this class.
- **Nobody had been reading the browser console as a standing step of any review, automated or manual.** It surfaced GAP-50 (a real `aria-hidden`-on-focused-ancestor WCAG violation in `Sheet.tsx`, live and reproducible) in under a minute, on the second sheet interaction tried. Cheap enough that there is no excuse to skip it — check console warnings/errors alongside any screenshot-based review from now on.
- **A route-def-by-route-def, screen-by-screen validation pass proves what exists matches spec — it cannot notice a flow that was never wireframed *and* never built**, because there is nothing on either side to diff. That is exactly how GAP-51 (F-1.7, "Set up the daily lease") went unbuilt through every prior pass: it has zero mentions in `ui-ux-guidelines.md` and zero implementation in `web/src`, so no comparison ever flagged a mismatch. None of this project's validation passes to date have enumerated `user-flows.md`'s full phase-1 flow list top-down against both documents at once. That audit hasn't run yet; F-1.7 falling through whole is reason to suspect it isn't the only one.
- **A migration comment can be right about its own object and wrong about the conclusion drawn from it — and it reads as authoritative either way.** `0003`'s header says revoked rows are excluded "so a revoked manager (F-1.4) can be re-granted". True of `0003`'s own index; false of the outcome, because `0001`'s `UNIQUE (business_id, user_id)` one migration above still blocks exactly that (GAP-52). The comment never looked up. **This is the third instance of the pattern §6 already names twice** — a stated reason that was accurate about the thing it examined and wrong about what it concluded. The habit that catches it: when a comment claims a *behaviour* is possible, check the other constraints on the same table, not just the one being added. It survived because nothing ever exercised the path — no endpoint has ever written `revoked_at`, so the claim was never tested against Postgres.
- **An accessibility assertion that watches for browser console warnings is worthless without `Accessibility.enable`, and it fails in the passing direction.** Headless Chromium computes the a11y tree lazily; with no client asking for it, checks like `aria-hidden`-on-focused-element never run and the warning is never emitted. The first version of `e2e/sheet-a11y.spec.ts` passed cleanly against code that was definitely broken. The fix is one CDP line (`await session.send("Accessibility.enable")`), but the habit that matters is the one that caught it: **before trusting a test that asserts the absence of something, make it fail on purpose.** Here that meant firing the exact violation by hand on `about:blank` and confirming the harness saw it — nothing, then two entries once a11y was enabled. Note also that `page.on("console")` alone is fine *once a11y is on*; the missing piece was never the listener.
- **`date AT TIME ZONE tz` and `timestamp AT TIME ZONE tz` are different overloads that produce different, silently-typed results — and "make it fail on purpose" catches a wrong fix, not only a missing one.** GAP-72's own suggested fix — `created_at >= $from::date AT TIME ZONE tz` — looked right and was wrong: Postgres upcasts the bare `date` to `timestamptz` at the **session's** zone first, then reinterprets that instant's wall-clock time in `tz`, landing eleven-plus hours off (`pg_typeof` even reported the result as `timestamp`, not `timestamptz` — a second, independent tell). Casting to a bare `::timestamp` first (genuinely naive, no zone attached) is what makes `AT TIME ZONE tz` read it as *that* wall-clock time *in* `tz`. **Verified directly against Postgres with a throwaway query, not assumed from the docs or from how the fix reads.** The discipline this confirms: running the new test against pre-fix code is necessary but not sufficient — run it against the *first-draft fix* too, before trusting that fix. Here, one of two new tests kept failing against the first draft; only the second run caught it.
- **`npm run typecheck` has now shipped broken twice, both times because the gate wasn't run before pushing.** `2822193` was the first (`api/vitest.config.ts`, TS4111). A0 was the second: `NewBusinessMember.role` was typed as the literal `"owner"`, so changing the one call site to `owner_manager` did not compile — found 7 Aug, a day after A0 shipped, by running `npm run check` for an unrelated reason. **The shape is worth naming: a type narrowed to the single value its only caller happens to pass.** It reads as precision and behaves as a tripwire on the next change; `role` is a set, and typing it as the set (`BusinessMemberRole`) is both more honest and less brittle. Note that no *test* failed either time — `test` and `typecheck` are separate scripts, and a green test run says nothing about whether the branch compiles.
- **A QA branch is only a meaningful live-verification target when it reflects what's actually merged.** `git log` is authoritative here, not the tracker's own "done" rows — A0 (`17da20d`) has been sitting on `build/p0-foundation`, unmerged into `develop`, since it shipped, so QA spent 6 August still running the pre-A0 signup path. Live-testing against a stale environment risks the exact failure it's meant to catch, inverted: a real fix reading as still-broken. Check `git log develop` (or the deployed commit) before trusting a live QA result to mean what it looks like it means.
- **A local branch ref is not the same fact as its remote-tracking ref, and `git fetch` only updates the second one.** Checking "has X been merged to `develop`" by diffing against a local `develop` that hasn't been checked out in days answers a question about a stale copy, not about what's actually on the remote — the exact inversion of the QA-staleness trap directly above, one layer lower in the stack. Diff against `origin/develop`, or fast-forward local `develop` first, before concluding a merge hasn't happened.
- **Before calling a single-writer column a bug, ask what the column is *for*.** A `grep` showing one writer proves one writer; it does not distinguish "everything else forgot to maintain this" from "this is a standing configuration and only one flow was ever meant to change it." GAP-54's first draft got that backwards and then went looking for live data to confirm the wrong reading — finding some, because a vehicle configured for daily lease with no daily lease yet *looks* like a stale figure and is in fact the ordinary case. The one-line answer was sitting in `createVehicle`'s own doc comment the whole time ("F-1.2 is what ever closes it"). **The distinguishing question is whether the column is derived from other rows or declared independently of them** — a derived one that nothing recomputes is a bug; a declared one with a single deliberate writer is a design, and its gap (if any) is the missing *flow*, not the missing writes.
- **An accessibility-tree snapshot taken immediately after a click can render before the async data it depends on has resolved, and the gap reads as real state.** Live-tested 7 Aug: a snapshot taken right after clicking a sheet's close button appeared to show a driver record that hadn't existed a moment before — momentarily indistinguishable from having just created one by accident. The network log settled it: the one `GET /api/driver` request for that page load, timestamped *before* the interaction in question, already carried that row in its response body — the earlier "0" was the query's loading state rendered as a fallback, not its resolved one. **Before concluding a UI action wrote something, check the network log for the actual request, not just the next snapshot** — this is the same discipline TRACKER already keeps for a11y console warnings (§5, `Accessibility.enable`) and it generalises to any assertion made from a point-in-time render rather than the data source itself.
- **A verification script nobody schedules can be wrong for over a week with nothing red anywhere.** `docs/engineering/fixtures/golden.py` — the actual script behind the "39 of 39" claim both `CLAUDE.md` and DM §16.1 make — stopped running on 1 August 2026, the day migration `0004` added `business_id NOT NULL` to `deposit_movement`, `insurance_claim` and `incident_recovery`; its own inserts into those three tables were never updated to match. Found 9 August verifying GAP-70/71's new DM §15 queries, purely because that pass happened to re-run it. **Deliberately not wired into CI** (`docs/README.md` calls it "supporting material"; IG §9.2's branch-count ceiling is part of why), so nothing else would have caught this either. The three protected figures (`134,000` / `15,000` / `7,500`) were never actually at risk — only the ability to prove them was, silently, for eight days. Fixed with the missing column on all three inserts; re-run confirms 39/39 (DM §16.1, DM v1.1.2). **A second, smaller gap found the same pass and left as found**: the script never writes a `business_member` row at all, so DM §15's held-per-partner query has nothing to select against it — worth fixing alongside the next thing that touches this file, not urgent enough to hold this one up.
- **`api` integration test files outside the ones a change directly touches can still depend on that change** — checking impact by filename match (touch `lease.ts` → re-verify `lease.test.ts`) misses siblings that hit the same endpoint under a different name. GAP-84 (F1, 8 Aug) added an arrangement check to `POST /api/lease`; the F1 session re-verified `lease.test.ts` and `dailyLease.test.ts` and called it done, but `lease-closure.test.ts` and `mileage-assessment.test.ts` (G-3's own fixture file) both also call that endpoint through their own local helpers and neither was touched. Invisible locally — nothing runs the full `api` integration suite by default (§1) — and invisible in the F1 session itself for the same reason; only surfaced 9 Aug when `integration.yml` ran for real on the PR and failed 10 assertions, all `lease-closure.test.ts:52`, all `expected 409 to be 201`. **The search that should have run was "every call site of the endpoint", not "every file with a matching name."** `grep -rl` for the route string across `api/tests/` found both missed files in one pass; fixed by giving all 21 affected vehicles the same `setVehicleArrangement(vehicleId, "A")` the two originally-checked files already had.
- **The connection-flakiness trap above (§5, "the Neon branch has a connection ceiling") got materially worse this session, not just recurring** — full-suite runs of `trip.test.ts`, `lease.test.ts` and `business-member.test.ts` hit multi-*minute* stalls (one run: 985,847ms on a 14-test file; another: 3,044s on `trip.test.ts` alone) rather than the instant `Connection terminated unexpectedly` the original trap describes, with a **different** test failing each retry and every failure clearing on an isolated or repeat run. Same root cause, same diagnostic ("moves between runs, in files the change never touched, is the environment" — do not chase it as a regression), but severe enough on this particular branch that **`TEST_PARALLEL=1` (already documented two bullets up) is worth reaching for by default now, not just as a known option**, and a single touched-file-plus-siblings run is cheaper to trust than a full-suite one when the branch is in this state.
- **`TEST_DATABASE_URL`'s own migration bookkeeping can silently fall behind the schema its tests actually need, and the two failure modes look identical from a test's own output.** Found 9 Aug: `business-member.test.ts` showed 4 failing tests (`POST /api/business-member/invite` and `.../change-role` all 500ing) that looked exactly like a pre-existing code bug — same shape as a dozen other "flaky/pre-existing" findings this session. `npm run migrate:status` (with `DATABASE_URL` overridden to `TEST_DATABASE_URL`, never the bare command — see IG §8.3) showed migration `0010` still `PENDING` on this branch despite being merged and deployed weeks ago; `business_member_invite` genuinely did not exist (`to_regclass` returned `null`). Applying it (`npm run migrate`, same override) fixed 3 of the 4 failures instantly, leaving only a genuine connection timeout. **Check `migrate:status` against `TEST_DATABASE_URL` before spending time diagnosing a cluster of same-shaped integration failures as a code regression** — a stale disposable branch (the `.dev.vars` comment on this one records it was created fresh, "test-parallel", specifically to dodge the contention trap two bullets up) is a real, ordinary explanation and costs one query to rule out.

**Writing code**

- **A U-3 prefill that crosses a direction-of-money boundary is the one prefill that must never be written, and this project has now reached for it twice.** U-3 ("sensible defaults, pre-filled") is a good rule that becomes a money bug the moment the source field points the opposite way from the target. The live case: `driverDayFeeMinor` (`packages/shared/src/schemas/driver.ts:23`) is money **you pay him**; `dailyLeaseAmountMinor` is money **he pays you**. Prefilling the second from the first seeds a plausible, wrong, unremarked figure into every record created. **This is not a hypothetical — UC §2's UC-04 note records that v1.1 of the specification itself called both a "per-day rate", and renaming them apart was a deliberate correction.** Plan.md's B10 write-up then re-proposed exactly the merge v1.1 had been corrected for, six days after the vocabulary lock was written down; it was caught by reading the schema rather than by any check. **Standing rule: before wiring any prefill, name the direction of both fields out loud. If they differ, there is no default — leave it empty.** The vocabulary lock (UI §9.6) exists to make this visible in copy; nothing yet makes it visible in code, which is why it needs to be a habit.
- **A bare single-statement write to an audited table records `changed_by` as `NULL`.** `withActor` wraps `.transaction`, so a write that never opens one is invisible to it. P9 fixed nine such functions by wrapping them even where atomicity was not otherwise needed. **Any new write to a `posted_period_id`-carrying table must open a transaction.**
- **`payment.amount_minor` has `CHECK (> 0)`** — a full reversal can never zero it. `status = 'reversed'` carries "nothing here counts"; the wire response reports the true remaining figure separately.
- **`tailwind-merge` does not know this project's scale.** Any new `--text-*` or spacing token must be added to `theme.text`/`theme.spacing` in `web/src/lib/cn.ts` or it is silently dropped next to a real colour class. Regression test in `cn.test.ts`.
- **`ownership_share` can never hold two open (`effective_to IS NULL`) sets for one vehicle — a second `POST /api/ownership-share` for a vehicle that already has a set always 400s.** `assert_shares_total` (migration 0001) sums every row whose date range contains the *new* row's own `effective_from`; a still-open first set's `[effective_from, ∞)` range contains any later date, so the total hits 200% and the trigger rejects it before a second set can ever exist. **This means `effective_to IS NULL` alone is a correct and sufficient "current split" filter** — not a coincidence, the deferred constraint's whole job — and a test that tries to `POST` a second set to prove otherwise needs a direct `db.insert` instead (found writing A2's `listOwnershipShares`, `partner.test.ts`'s own comment records the reasoning).
- **A `GENERATED ALWAYS` column reads back nullable through Drizzle even though Postgres never actually leaves it null.** `banking_event.discrepancy_minor` (`recorded − counted`, migration 0001) is one; a raw `SELECT` of it types as `bigint | null` in Drizzle regardless of the `NOT NULL` guarantee the two source columns give it. Defaulting the gap with `?? 0n` is exactly the W-56 pattern the lint rule exists to catch (and it caught it) — compute the figure from the two real columns instead, the same way `recordBankingEvent` (domain/partner.ts) already does on write, rather than trusting the generated column on read.
- **"A row exists for this idempotency key" is not the same fact as "this action already happened", the moment something *other* than the action itself can create that row (GAP-3).** `confirmDay` was idempotent on `(daily_lease_id, business_date)` since P3, correctly, right up until P13 added a second writer (`generate-day-cards`) that inserts the same row in a placeholder `open` state before the user ever acts. The idempotency check kept matching on existence alone and started silently no-op'ing real taps against real money. The fix — and the pattern for the next table that grows a second writer — is to gate the no-op on the row's own **state**, not its presence: a row in a non-terminal/placeholder state is the write path (an `UPDATE`, guarded on that same state in the `WHERE` clause so a concurrent racer's write affects 0 rows instead of throwing), and only a row already in a terminal state is the genuine no-op. Worth checking any other `find-then-return-if-exists` idempotency guard against whether a cron can now produce that same row ahead of the user — `day_record` was one of at least two tables (`vehicle_day_allocation` is the other, cron-only, no user-facing write competes with it today) P13 turned into a second writer.
- **A new invariant trigger firing on `INSERT` "because the reference implementation does" is a copy of the wrong half of the pattern.** `assert_business_has_owner()`'s (A11/INV-31) first draft matched `assert_shares_total`'s exact shape — `AFTER INSERT OR UPDATE`, deferred — and broke roughly a dozen existing integration-test fixtures that mint a `manager` as a business's sole member, because an `INSERT` can only ever *add* a row and can therefore never by itself take an active-owner count to zero; only an `UPDATE` that sets `revoked_at` can. `assert_shares_total` genuinely needs `INSERT` (a 60/40 split is built from inserts), which is exactly why copying its trigger *shape* without re-deriving which statement types can actually violate the *new* invariant produced a check that rejected valid, unrelated writes for no protective benefit. Ask "which statement type can actually cause the bad state" before choosing `INSERT`, `UPDATE`, or both — never default to "both" because a nearby trigger does.

**Three form bug classes, fixed structurally — every new form inherits the fix**

Found in P2 and fixed once each, at the structural level rather than per-form. A new form that hand-rolls around any of them is reintroducing a solved bug:

1. **Wire/domain mismatch on any zod schema with `.transform()`** (`moneyWireSchema`, `businessDateSchema`) — its `z.infer` output type differs from its `z.input` wire type, but `MoneyField`/`DateField` produce and consume the *domain* type. The fix: a form-local schema built from `z.custom<Minor>`/`z.custom<BusinessDate>` with no transform, keeping form state in domain types throughout, converting to wire via `toWire()` **only inside `mutationFn`**.
2. **`""` vs `undefined` on optional text inputs** — a native `<input>` always yields `""` when untouched, but `z.string().min(1).optional()` only skips validation for `undefined`. Fixed once in `lib/optionalTextField.ts`'s `blankToUndefined`, spread into `register(name, …)`.
3. **A cross-field error hidden inside a collapsed `Disclosure`** — W-55's error attaches to a level-2 field, invisible on a failed submit. Fixed by `Disclosure`'s `forceOpen?: boolean`, driven by `errors.fieldName !== undefined`.

**Migrations** — forward-only and numbered. `0001` DDL · `0002` audit trigger · `0003` single active membership · `0004` `business_id` on seven audited child tables · `0005` odometer `(lease_id, read_on)` partial unique · `0006` **`assert_period_open()` only fires on `INSERT` or an `UPDATE` that actually changes `posted_period_id`** — settling a claim or obligation months later is legal and was being rejected · `0007` `expense.voided_by` · `0008` **narrows `0006`'s exception to exclude a void** (`voided_at` `NULL → NOT NULL`) — GAP-35, A9a · `0009` widens `obligation_kind_check` to admit `trip_fare` — A6 · `0010` **`business_member`'s pair-unique made partial** (GAP-52), an explicit audit trigger (GAP-53), `business_member_invite`, **INV-31** (`assert_business_has_owner()`, `AFTER UPDATE` only — see §5 above for why not `INSERT`) — A11. MP-04 (nested pickers) reproduced too, and worse than documented — the source audit predicted a parent sheet closing; live, the entire in-progress form state (a party selection and an amount) was discarded with it, no error. **MP-08 (the `Dialog`-in-`Sheet` stacking watch item) could not be tested, and not because of a tooling limit**: reading `AdvanceSheet.tsx` to find a way to seed its precondition found that the client has no way to attach an advance to a trip at all — a gap in its own right, folded into **GAP-100** rather than filed separately, since it's the same functional area found incomplete a second, deeper way.
30. **The cash-position mislabelling is the same shape GAP-75 already taught this queue to watch for, in a screen that shipped ten days after GAP-75 closed.** `CashPositionReportScreen.test.tsx` asserts "held for customers" as the correct rendering of a number the server explicitly, deliberately, does not attribute to any party type — the test encodes the assumption instead of checking it. **Filed as GAP-106.**
31. **Everything else checked live either confirmed a prior fix or found nothing.** LT-7/GAP-3 is now closed in full — the two-visit cron test that had sat open since 6 August finally got its second visit, and the placeholder the cron produced confirmed correctly on the first tap, all three money facts written in one transaction. GAP-84's arrangement gate and GAP-85's blank-vs-zero fix both held under conditions slightly harder than their original tests — direct URL navigation for the former, a fresh trip form for the latter. Dark mode was checked across every screen this pass touched and found genuinely improved since 8 August (the voided-expense treatment now carries a badge and a border, not only strikethrough text) with nothing new wrong.

**What this pass is worth, stated fairly, the way every pass before it has been:** it produced one finding (GAP-103) more severe than anything in this tracker's 106 gap ids, and it produced it by doing the one thing eight prior source-only and live passes had no way to do — committing real data through a real write path and then checking a real report against it, weeks after both existed. The lesson is not "live-test more" in the abstract; it's the same one LT-5's own 8 August note already stated in advance, and was simply too early to act on: **a verification blocked on a screen not existing yet is not the same as a verification that happened.**
